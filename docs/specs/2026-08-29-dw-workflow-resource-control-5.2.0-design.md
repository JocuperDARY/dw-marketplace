# development-workflow 5.2.0 资源控制设计

- 状态：设计草案已完成，等待审阅与后续实施审批
- 日期：2026-08-29
- 基线：`0c1d70cc2dc0fa0028c8fffab317ff29e283c19c`（development-workflow 5.1.0）
- 本文只定义 5.2.0 的行为、边界和验收条件，不授权实现、GPU 运行、提交或发布。

## 1. 目标与不做事项

5.2.0 在 5.1.0 的协作规则和校验格式上增加可执行的任务级资源控制：统一登记任务拥有的进程、终端、临时目录等资源；可靠回收子资源；阻止重复失败造成无效修复循环；根据硬件需求和预计时长调度可并行任务；向用户清楚说明资源、进度、失败和清理状态。

本版本不增加 daemon、数据库、私钥或常驻服务，不全面重构 `dw-collaboration`，不修改 `gpt-bridge`，不放宽现有身份和路径安全判定，也不引入与风险不相称的全面审查。本文不要求新的运行时依赖。

## 2. 5.1.0 现状与需要补充的能力

5.1.0 已有 `ResourceLedger1`、只追加且不改旧记录的事件（append-only events）、复合进程身份、临时目录安全判定、重试预算和 `HOLD`（停止自动动作并等待确认）结果；这些是 5.2.0 的兼容基础。当前需要补充的能力是：

- 规则分散在 Skill、reference 和 validator 中，缺少任务运行时可直接使用的 `TaskResourceTracker` 与嵌套 `ResourceScope`；
- ledger 能描述资源，但没有统一实现登记、监控、异常恢复、逆序回收和幂等关闭；
- 失败指纹主要由调用方提供，无法阻止调用方通过改写描述或命令包装重置预算；
- 没有依据 GPU、CPU、内存、I/O 和预计时间进行准入、空隙补位（backfill）、动态补位与受控并发的队列；
- 用户说明尚未形成稳定的开始、进度、失败和收尾格式。

## 3. TaskResourceTracker 与 ResourceScope

### 3.1 登记和身份绑定

`TaskResourceTracker` 是纯核心状态机，不直接启动、终止或删除资源。每个任务先打开根 `ResourceScope`；子任务或子命令只能在父 scope 下取得子 scope。登记记录至少包含：`resource_id`、类型、`owner_id`、`parent_resource_id`、scope 与 lease generation、用途、配额、关闭条件、登记顺序、当前状态和证据引用。

资源真正出现后，宿主执行适配器（host adapter）提交受信观察，tracker 才把登记项绑定到实际身份。5.1.0 的进程与临时目录判断函数固定由 tracker 调用，普通调用方不能替换。临时目录使用的真实文件系统 resolver 在 tracker 构造时一次性注入，单次 observation 内携带的同名函数会被忽略。进程身份继续使用 5.1.0 的 PID/handle、启动时间、可执行文件与参数哈希、父身份、启动随机标识（launch nonce）、记录代次（generation）、工作目录/端口/用途及可用的宿主运行 ID；路径身份继续包含规范路径、父目录身份、平台、记录代次、链接或目标替换检查和活动句柄状态。计划、名称、PID、TTL 或文本形式的路径本身都不能证明所有者。所有者、父资源或身份缺失、漂移、冲突时进入 `HOLD`，核心不得猜测所有者。可能授权精确终止、临时目录回收或释放的观察还必须由宿主管理的观察接口确认；调用方布尔值本身不算确认。

### 3.2 监控、关闭和异常恢复

tracker 按注入的有界策略观察 liveness、身份、资源用量、最近进展和关闭条件。不同资源仍需满足 `ResourceLedger1` 的类型专用证明，例如 agent session 的 child closed、terminal 的 terminal absent、port 的 port absent、受限计算的 compute released。保留的 artifact 使用单独的 retention 证明并保持 `RETAINED`。tracker 只保留实际发生的观察和决定，不自行设置通用轮询频率或阈值，也不合成未发生的 ledger 动作。

`ResourceScope.close(reason)` 先停止新登记，再按“更深子 scope 优先；同一 scope 内按成功取得资源的逆序”生成关闭决定。对每项资源保持现有顺序：请求优雅停止、限时观察、重新核对完整身份、仅在 `MATCH` 时请求精确回收、验证不存在，再释放父 lease。一个子资源未验证回收时，其父资源不得标记为已回收。

close 以 `scope_id + generation` 为幂等键。已完成的重复 close 返回同一结果，不再次执行动作；中途失败的重复 close 只恢复仍待处理的步骤；身份已变化则停为 `HOLD`。正常退出使用 `finally` 关闭 scope。历史中的每条记录绑定所有者、run、generation、上一条记录的哈希和自身哈希，并保存当时的决定及每次 close 结果。任何 live state 变化前先预留本次所需的全部历史记录；首次 close 同时预留 request 与 evaluation 两条记录，任一数量或字节上限失败都不得留下半完成状态。恢复时还必须由宿主管理的历史接口确认预期的最终哈希。哈希用于发现内容变化，不能单独证明记录来自可信宿主。宿主或进程异常重启后，再用新的宿主观察逐项核对；证据不足时只观察和保留现场，不能据旧 PID 或旧路径清理。

### 3.3 宿主执行适配器的边界

核心只产生决定，宿主执行适配器只执行已经通过 5.1.0 安全判定、权限判定和当前授权范围批准的精确动作。适配器必须返回动作、目标复合身份、开始/结束时间、结果和回收后观察；请求已提交不等于动作成功。适配器不得扩大目标、改用进程名或通配符，也不得把失败的安全判定替换为“尽力清理”。

## 4. FailureLoopGuard

`FailureLoopGuard` 从当前任务的历史自行计算失败身份，不接受调用方给出的最终失败指纹（fingerprint）。规范化输入包括阶段与失败检查点、错误类别/代码、规范命令或测试 ID、相关输入与产物哈希、可观察的环境身份、副作用状态及时间顺序；提示文本、包装命令、日志文件位置和无关时间戳不参与身份。计算规则必须确定、版本化并有固定测试向量。run 和 guard ID 对应的宿主存储保存预算、总结和已经使用的退出次数。每次保存绑定单调 revision、上一状态 hash、compare-and-swap 确认、精确回读和宿主 current-state resolver；旧快照、并发旧写者或无实际写入的假成功都必须停止。保存失败时所有内存预算和历史恢复到最后一次成功状态。

该模块分开管理 `retry_budget`（重试预算）与 `repair_budget`（修复预算）：

- 重试仅用于经宿主确认属于暂时性故障、没有未知副作用、具有幂等键和已命名重试策略的尝试；相同失败身份重复出现或预算耗尽时停止继续尝试，并停止新的任务委派；
- 修复仅用于宿主可解析的证据指向代码缺陷，且修复假设、变更范围、变更哈希和验证方法明确的情况；换措辞、换包装命令、重复检查或重启会话不能重置预算；
- 只有新的、可引用证据改变失败分类、根因假设、受影响范围或验证结论时，才能形成新的失败记录代次。新日志行本身不算新证据；
- 权限、网络、磁盘、驱动、依赖服务、sandbox 或不可用硬件等环境类问题不得触发代码修复。它们只能进入有界重试、等待外部状态、请求用户授权、环境修复建议或 `HOLD`。

每次决定向用户说明失败身份摘要、已用/剩余预算、新证据、下一检查点和停止条件，但不泄露密钥等敏感信息或原始提问内容。

相同失败重复出现或修复预算耗尽时，第一步必须停止该工作单元的新重试、新修复和新委派，然后生成一次简短的循环总结（`LoopSummary`）。总结至少记录：共同失败身份；首次和最近发生时间；重试与修复次数；尝试过的根因假设和实际修改；一直不变的观察；真正新增的证据；环境、权限和依赖状态；已知副作用；最后成功状态；仍在运行或待回收的资源；需要用户决定的事项。同一失败记录代次再次触发时复用同一总结，不生成新的总结；总结本身不能重置重试或修复预算。

总结后只选择一个有证据支持且在权限范围内的循环退出决定（`LoopExitDecision`）：缩小问题并构造最小复现；改用能区分根因的观察方法；切换经过说明的实现或算法路径；仅在已授权且可逆时恢复到已知可用状态；等待并观察外部条件；请求用户决定或授权；停止工作并保存证据。没有证据的临时绕路方案、换模型、换代理或改变命令措辞都不是退出方法。

退出决定必须记录所选方法、依据、最多一次有界下一尝试、成功与失败判据、明确不会做的动作和清理条件，也不能重置预算。该有界尝试若再次得到相同失败且没有新证据，直接停止，不得进入“总结—尝试—再总结”循环。若没有安全退出方法，则停止新工作，回收已确认属于本任务的资源，保留诊断证据并向用户说明阻塞。

## 5. 资源感知并行队列

### 5.1 资源画像与准入

每个任务在进入 ready 前提交版本化资源画像：精确的 tracker owner/run/scope/generation、非空 `trackedResourceIds`、授权引用、GPU 型号/能力要求与数量、设备独占或明确共享方式、显存软/硬预算、CPU 核数、RAM、I/O 类型与预算、预计时间范围及估计来源/置信度、依赖、优先级、最晚开始条件，以及前台或外部任务需要保留的资源。队列开始前由 tracker 把该 scope 和资源集合一次性认领给一个 task；空 scope、缺少绑定资源或第二个 task 复用同一 scope 都进入 `blocked`。

准入控制必须确认：依赖已满足；画像完整；宿主能观察所需指标；TaskResourceTracker 中对应的精确 scope 仍可使用；宿主授权接口接受该引用；候选资源满足型号、能力、独占设备数量、显存和安全余量；不会越过前台/外部 lease、温度/功耗策略、显存硬上限或用户授权。信息未知时进入 `blocked`，不能乐观分配。

最小队列状态是：

- `ready`：依赖、授权和画像有效，等待资源；
- `running`：已绑定 ResourceScope 和实际占用，持续监控；
- `blocked`：依赖、证据、授权或资源不满足；
- `draining`：不再接收新工作，正在停止、取消或回收。

完成、失败和取消是终态结果，不复用为资源已释放的证明；只有对应 scope 验证关闭后，队列才释放占用并允许补位。

### 5.2 空隙补位、并发和动态补位

调度以多维资源需求和安全余量决定并发，不以任务数量或单一 GPU 百分比决定。队首长任务暂时缺少完整资源时，补位任务只有在其最大预计时长不超过“补位上限和长任务剩余等待时间”两者较短值时才能启动。5.2.0 没有 pause/checkpoint 执行状态机，因此 `preemptible=true` 不放宽这条规则。达到最长等待时间的任务先于刚进入队列的高优先级任务。没有稳定 GPU 设备 ID 时，shared 与 exclusive 模式保守互斥。队列还设置任务数量上限，只有已确认释放且不再被依赖的终态记录可以移除。

任务启动、完成、超时、失败或取消时都触发 draining；只有 TaskResourceTracker 验证相关进程、显存、端口、句柄和临时 allocation 已释放，调度器才按最新画像动态补位。监控或身份不完整时停止补位。受控并发上限来自注入的宿主策略、真实资源和前台保留量，不使用硬编码的通用并发数。

GPU 显存占用和有效计算利用率必须分别监控：显存已分配不代表 GPU 正在做有效计算，短采样尖峰也不代表持续吞吐。可调度显存池定义为“物理显存减去驱动、桌面、外部任务占用和宿主安全余量”，不是物理总显存。**有真实可运行任务、workload 可并行、宿主策略允许且前台与外部任务不受影响时，以时间窗内任务对可调度显存池的占用率和有效 GPU 计算利用率均不低于 85% 作为良好情况的优化目标。** 这不是所有任务的硬验收，也不是准入或完成条件。

判断调度质量必须同时看时间窗统计、有效吞吐、完成/失败率、显存不足（OOM）、重试、温度或功耗降频，以及前台响应。安全余量、任务画像硬上限、显存不足或降频风险和前台响应约束始终优先。短任务的短采样尖峰、低并行度工作、数据加载瓶颈、内存受限任务和算力受限任务应单独解释；低显存但计算受限的工作负载不得通过无价值的显存分配填满显存。禁止通过空转、虚假工作负载或无业务价值的复制任务提高指标；禁止为追求 85% 超额分配，造成显存不足、热降频、交互卡顿，或破坏前台/外部任务。出现这些风险时应降低并发、停止补位或进入 `HOLD`。

## 6. 工作强度与用户说明

工作强度只改变观察频率、证据深度和复核范围，不改变安全不变量：

| 档位 | 适用范围 | 最小行为 |
|---|---|---|
| `light` | 单一、短时、低风险、机械可验任务 | 一个根 scope；开始和结束核对；自动静态检查 |
| `standard` | 多步骤或多个本地资源的普通工程任务 | 分阶段 scope；有界进度观察；focused tests；失败预算 |
| `high` | 长任务、并行调度、昂贵资源或高后果操作 | 持续窗口化观察；独立回收复核；残留风险与恢复证据 |

任何档位都必须执行精确进程身份核对和安全路径删除判定；这两项不可降级。档位也不能扩大权限、修改既有授权或把计划当作执行证据。

面向用户的说明遵循四个节点：开始前说明任务范围、资源画像、并发/前台保留和停止条件；长任务进度说明完成/失败/待处理数、有效吞吐、资源时间窗、最新产物、队列状态和下一检查点；失败时说明失败分类、预算、新证据和是否需要授权；结束时说明结果、验证、已回收与未验证资源、残留进程/目录/句柄及恢复办法。只报百分比或只说“已清理”不合格。

## 7. 兼容性与建议实施边界

5.2.0 保持 `CapabilityMatrix1`、`CollaborationPlan1`、`ResourceLedger1` 和 `ExecutionReceipt1` 的 5.1.0 含义。队列状态不冒充 ledger 资源状态；`exportLedgerProjection()` 只输出来自实际 tracker history 的提示，并明确标记 `projectionIsResourceLedger: false`。它不生成未实际发生的 start、quiesce、exit、reclaim 或 retention 事件。宿主必须从动作回执重新构造并验证真实 `ResourceLedger1`，最终完成链仍是 `ResourceLedger1 -> ExecutionReceipt1`。确需 schema 新字段时必须可选、版本化，并证明旧 artifact 仍可读取。

建议后续实现只触及：

- `plugins/development-workflow/skills/dw-collaboration/SKILL.md`
- `plugins/development-workflow/skills/dw-collaboration/references/resource-lifecycle.md`
- `plugins/development-workflow/skills/dw-collaboration/references/resource-control.md`（新增）
- `plugins/development-workflow/skills/dw-collaboration/scripts/lib/task-resource-tracker.js`（新增）
- `plugins/development-workflow/skills/dw-collaboration/scripts/lib/failure-loop-guard.js`（新增）
- `plugins/development-workflow/skills/dw-collaboration/scripts/lib/resource-aware-queue.js`（新增）
- `plugins/development-workflow/test/resource-control.test.js` 与 `resource-aware-queue.test.js`（新增）
- 版本、测试脚本和发布说明所必需的 package、plugin、marketplace 与 README 元数据文件。

除非测试证明上述边界不足，否则不修改 hooks、`gpt-bridge`、其他子 Skill 或既有 schema。未来实施必须更新 plugin 版本到 5.2.0，但本设计阶段不改版本文件。

## 8. 测试与验收

后续实施至少覆盖：

1. 资源在实际出现前后分别登记与绑定；owner/parent/generation 或复合身份漂移会 `HOLD`。
2. 嵌套 scope 按子级和取得顺序逆序关闭；重复 close 无重复副作用；异常历史可恢复，证据不足不清理。
3. host adapter 拒绝未通过现有安全判定或超出授权的动作。
4. guard 从历史稳定计算失败身份；包装变化不重置预算；真正新证据形成新 generation；环境问题不会生成代码修复动作。
5. 失败触发后先生成总结再允许下一动作；同一代总结幂等复用；退出方法受证据和权限限制；无安全方法时停止、清理已确认资源并请求用户决定；总结不重置预算；唯一有界尝试再次得到相同失败且没有新证据时直接停止，不进入“总结—尝试—再总结”循环。
6. 队列准入、四个状态、长短任务 backfill、防饥饿、受控并发、动态补位和所有终止路径释放占用均有确定性测试。
7. GPU 显存与有效计算指标分开；短尖峰、低并行度、I/O/内存/算力瓶颈有例外用例；85% 目标不会导致虚假负载、超额分配、OOM、降频或前台退化。
8. `light/standard/high` 只改变观察和复核强度，精确进程身份与安全路径回收在三档全部执行。
9. 用户说明包含开始、进度、失败和收尾所需字段；既有 5.1.0 artifacts 与测试继续通过。

测试应使用合成画像、受控 marker 进程和任务自有临时根，不启动真实 GPU workload，不依赖网络，不安装新依赖。完成检查点是 focused tests、现有全套测试、package dry-run、diff 检查和零任务自有残留资源；静态检查不得冒充真实资源运行证据。

## 9. 未来方案：向更强模型提问并保存 Markdown

- 状态：`OPEN / DEFERRED`
- 归属：未来独立设计与授权；不属于 5.2.0 实现范围，也不在 §7 允许修改的文件范围中。

本轮不选择供应商、不调用 API、不写实现。至少有两组未知面需要先验证：

1. OpenAI、Anthropic 等在请求结构、消息角色、工具调用、流式事件、错误和输出封装上不同。未来需要供应商适配器（provider adapter）、规范化的内部请求/响应模型和当前会话能力探测（capability probe）；不能假定接口兼容，也不能把请求成功当作目标模型完成回答。
2. 若目标模型需要理解项目，必须提供受控项目上下文包（context package），至少包含适用的 AGENTS/Skill 指令、选定文件、diff/manifest、问题、每项来源与哈希、截断规则、token budget 和敏感信息过滤；另一选择是在语义兼容的运行工具环境（harness）内执行。普通一次 API 文本请求不等于 project-aware agent。

还需单独验证代理运行框架（harness）、可用工具、沙箱限制、MCP 和工作目录的行为是否一致。凭据使用、费用、网络访问和数据外传分别需要明确的用户授权，不能从“保存回复”推导授权。

### 9.1 每次调用和列表刷新都需批准

每次真正调用付费模型 API 前，都必须取得单次、明确的用户批准。批准前展示：供应商、endpoint、模型、预计最大输入量和输出量、可估算时的最高成本、会离开本机的项目上下文清单摘要、使用的 key 别名或脱敏短指纹、超时与取消条件，以及 Markdown 输出文件。供应商、模型、endpoint、上下文或费用上限有实质变化时必须重新批准；安装或配置该功能不等于批准调用。

查询或刷新模型列表同样是使用凭据和网络的 API 操作，不能在后台自动运行。每次刷新前都要取得明确批准。刷新失败时保留旧列表，但必须标记为 `stale`（可能过时）并记录刷新失败；不得伪造新列表或把旧列表标成最新。

### 9.2 长期供应商登记表

未来可设计长期存在的供应商登记表（`ProviderRegistry`）：它是用户级、版本化、位于仓库外的普通配置。本设计不决定真实路径，也不创建该文件。登记表可记录 `provider_id/display_name`、`base_url`、`api_family`（例如 `openai-responses`、`openai-chat`、`anthropic-messages`、`custom`）、`api_version`、认证方式、`secret_ref`、key 别名与不可逆短指纹、请求消息封装、流式输出/工具调用/错误适配器、模型发现 endpoint 与解析器、模型列表及来源、`last_refresh/last_success/stale` 状态、供应商确实返回的模型能力/上下文窗口/价格，以及默认超时和取消方式。

模型列表必须绑定到刷新时使用的供应商、API 地址、`api_family`、`secret_ref` 和 key 短指纹；其中任何一项变化，都先把旧列表标记为 `stale`，不能继续把它描述为当前 key 的模型列表。模型列表只表示供应商报告当前凭据可以看见这些模型，不自动证明每个模型都能成功调用。真实可用性必须通过另一次获批调用验证。不同 `api_family` 必须由各自的消息、流式输出、工具调用和错误适配器处理，不能按字段相似就假定兼容。

API key 明文不得写入 `ProviderRegistry`、仓库、Markdown、日志或测试 fixture。真实 key 由操作系统凭据存储或等价的秘密存储管理；登记表只保存 `secret_ref` 和不可逆短指纹。宿主没有安全凭据存储时，该功能保持不可用，或由用户每次临时提供；不得降级为明文长期保存。日志和错误必须删除 `Authorization`、其他认证 header 和 key 内容。

登记表更新必须避免部分写入；schema 版本不兼容时拒绝猜测迁移。该未来方案不引入数据库或 daemon，也不属于 5.2.0 允许修改的文件范围。

保存的 Markdown 只算咨询证据，必须记录 provider/model、时间、request ID（可用时）、context manifest、限制和未验证项。它不能证明代码已执行、测试已通过或任务已完成。

以后决定是否实施前，先做一个无项目写权限、无工具副作用、使用固定小型项目上下文包的最小原型；建立兼容性矩阵，逐项记录消息、流式输出、工具调用与错误、取消、限额、数据保留和实际模型元数据；回答以下验收问题：上下文是否完整且可审查，敏感信息是否被阻止，成本和取消是否可控，失败能否确定归类，Markdown 能否对应到同一份项目上下文清单，宿主能力不足时能否停止而不是继续猜测；逐次调用批准是否有效；刷新模型列表是否需要批准；密钥是否从不进入普通文件或日志；旧列表的 `stale` 状态是否准确；不同 API family 的消息、流式输出、工具调用和错误是否由各自适配器处理；项目上下文或费用上限漂移时是否重新批准。只有这些问题有证据后，才另行设计实现文件范围和授权边界。
