# API 设计

## 核心原则
- 先识别目标系统既有的协议、客户端与兼容性要求，再选择 API 风格
- REST 风格可采用资源命名（如 /users、/orders）；版本化、错误和分页格式沿用已确认的系统契约
- 新增或改变格式时明确兼容策略、错误语义和验收证据

## 设计清单
- [ ] 资源、方法、参数和响应语义符合所选协议与既有客户端契约
- [ ] 过滤、排序和分页包含明确的默认值、边界与授权约束
- [ ] 创建、更新、删除的状态码和响应体按实际语义确定，不套用统一响应码
- [ ] 有重试或缓存行为时，确认幂等性、安全性和失效条件
- [ ] 限流策略与对外字段有明确约定，不假定固定头名称
- [ ] 维护仓库已有的 OpenAPI 或其他接口文档与相关契约测试

## 错误格式示例

以下仅示范结构；字段、错误码及对外信息范围以目标 API 契约为准：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Email is required",
    "details": [{"field": "email", "reason": "missing"}]
  }
}
```

## 工具链
- 先发现当前可用的 API 设计、接口审查和文档校验能力，优先复用项目原生工具
- 专用 Skill 可用时按任务采用；缺少某个外部名称不阻塞等价检查
