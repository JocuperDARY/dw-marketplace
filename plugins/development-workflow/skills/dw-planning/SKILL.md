# 方案设计与操作指引先行（Planning & Operation Guide）

> 本 skill 是 [development-workflow](../development-workflow/SKILL.md) **L1 研发主生命周期** 的子模块，覆盖 **阶段二：方案设计与计划编写**。遵循铁律 B1（计划先行，执行在后）。

**核心原则：在实施前消除会改变范围、风险或验收方式的不确定性；计划的详细程度与风险相匹配。**

---

## 计划深度

| 条件 | 计划形式 | 必含内容 |
|------|----------|----------|
| 局部、可逆、无关键取舍 | 简短计划 | 目标、改动位置、验证方式 |
| 行为变更或多个关联文件 | 标准计划 | 背景、步骤、验收标准、风险 |
| 跨模块、安全/数据敏感、不可逆或有外部副作用 | 完整操作指引 | 候选方案、取舍、分阶段计划、回退与授权点 |

只有存在真实取舍时才要求多个方案。显而易见的修复不为凑数制造备选；先记录为什么选择直接方案。

计划列出真正影响执行的依赖、验收和未决问题。已有授权覆盖后续动作时继续推进；“写完计划”“进入下一阶段”本身不是新的审批点。用户要求先看方案时，遵守其明确的等待要求。授权与资源判断见 [总纲](../development-workflow/SKILL.md#授权资源与内部前置条件)。

需要多角色协作时，使用 [团队职责与交接](../dw-collaboration/references/ordinary-collaboration.md) 划分写入范围、依赖和结果回传。计划可以建议协作方式；实际启动仍取决于当前委派权限与可用能力，不能把计划中的角色列表当成必须创建的团队。

## 证据优先的逐层追问

先从当前文件、运行结果和用户已给信息核对事实，再列会改变方案的决定及其依赖。每轮只问前提已明确的关键决定，给出建议与取舍；互不依赖的问题可以合并，依赖尚未回答的问题留到后续。可自行查明的事实由执行者调查，不转交用户猜测；调查中的前提只影响依赖它的分支。

已明确的目标和约束直接沿用。关键分支已解决、剩余假设可验证且不会扩大授权或风险时结束追问，进入相应工作；不为穷尽所有想象中的分支持续访谈。用户明确要求先确认时再等待确认。需要压力测试方案时，按需读取 [方法整合说明](../dw-reference/references/method-integration.md#方案压力测试)。

## 完整操作指引结构

```markdown
# 操作指引：[方案名称]

## 1. 背景与动机
### 1.1 问题描述 / ### 1.2 问题特征分析 / ### 1.3 影响范围

## 2. 方案探索（发散阶段）
### 方案 A：[名称] — 核心思路、优点（尽量量化）、缺点/代价、取舍点
### 方案 B：[名称]（存在真实备选时填写）

## 3. 选定方案与理由
- 选择方案、理由（数据或逻辑推导）、舍弃方案及原因

## 4. 实现计划（收敛阶段）
- [ ] 步骤 1：[描述] → 验收标准：[如何确认] → 涉及文件：[路径]

## 5. 回退计划
- 失败判定条件、回退操作、保留的中间产出
```

> 需要参考完整填写示例时，按需读取 [完整填写示例：API Redis 缓存层操作指引](references/operation-guide-example.md)。

## 阶段投入原则与粒度标准

- **投入比例**：不预设固定时间比例；按未知量、失败代价和验证成本分配精力。方案已由仓库约束决定时快速收敛；存在外部副作用或不可逆步骤时增加规划与回退演练。验证预算与实现同时确定，不临时压缩。
- **独立边界**：每个子步骤应形成一个可独立验证、必要时可回退的变更单元，并附带可核验的产出物（测试通过、文件存在、输出值在范围内）。
- **增量工作包**：多步骤计划写明涉及文件、消费与产出的接口、关键反例、检查命令、预期结果及停止条件。准备、配置和文档并入需要它们的交付，避免过度碎片化；同类机械改动可以合批。详见 [增量工作包](../dw-reference/references/method-integration.md#增量工作包)。

### 跨宿主分层 TODO 与计划跟踪（Cross-Harness `DwTodoPlan1`）

当当前宿主缺少原生的持久 TODO、阶段依赖（DAG）或跨进程同步能力时，可按需使用本目录的可选脚本 `scripts/todo-plan.js`（详见 [分层 TODO 与计划管理器](references/todo-plan-manager.md)）。它提供阶段—任务两级 5 态跟踪（`pending`/`in_progress`/`completed`/`impossible`/`error`）、动态拆改（`split-task`/`apply`）、文件锁事务及终端/Markdown/静态 HTML 派生视图；默认仅由总控写入，也可通过 `DW_TODO_PLAN_PATH` 在共享工作区开启角色隔离与加锁协作。该工具只管理计划状态与视图，`check-complete` 不替代独立测试、审查或宿主验收。

## 回退策略

- 优先复用 Git 历史；覆盖独有数据或执行难以回退的操作前备份一次，并写明恢复办法
- 冒烟先行：投入全量资源前，先用最小规模实验（1 个数据单元、1 个配置）验证
- 明确"不可回退"的步骤（如覆盖生产数据），提前确认

## 规划阶段反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 没有明确目标和验收就写代码 | 方向性错误、返工 | 先写与风险匹配的计划 |
| 计划太粗 | 遗漏关键步骤、无法对照检查 | 分解到可独立验证和回退的粒度 |
| 为明显修复强造多个方案 | 增加噪声、掩盖真正取舍 | 无真实备选时记录直接方案及约束 |
| 计划不考虑回退 | 失败时无法恢复 | 复用版本历史，独有数据按需备份，冒烟先行 |
| 计划不写验收标准 | 不知道何时算完成 | 每个子步骤有可核验的产出与明确判据 |
| 原因未知就直接修 | 治标不治本，问题复发 | 先取得足以区分根因的证据（参见 dw-diagnosis） |
