# 诊断与调试方法论（Signal & Pipeline Debugging）

> 本 skill 是 [development-workflow](../development-workflow/SKILL.md) **L2 专项技术深潜** 子模块，专注 **中间态信号诊断、反向验证与全生命周期链路排查**。宏观原因分类与优先级排序见 [dw-diagnosis](../dw-diagnosis/SKILL.md)。

---

## 按假设选择观测方法

| 当前问题 | 可区分假设的证据 | 详细方法 |
|----------|------------------|----------|
| 性能或资源瓶颈 | 代表性负载、热点、耗时和资源等待 | [dw-optimization](../dw-optimization/SKILL.md#性能分析流程) |
| 数值或业务结果偏差 | 相同输入下的结果、领域不变量、单变量对照或消融 | [dw-verification](../dw-verification/SKILL.md) |
| 管道未激活或信号异常 | 入口、输入、状态转换及下游消费证据 | 下文信号检查与链路排查 |
| 场景间表现不一致 | 受影响的代表性场景、边界和错误路径 | 按各场景预先定义的行为对照 |

先选择最能区分当前假设的观测点。工具按当前环境能力发现，诊断结果与最终验收结论分别记录。

---

## 隔离实验与证据记录

1. **最小独立复现（Minimal Reproducer）**：隔离与故障相关的最少依赖；必要时绕过项目框架直接调用底层 API，规模以能复现且便于审查为准。
2. **对照条件明确**：每次尽量只改变一个待检验变量，保持其他输入、配置和环境可比；无法控制的差异单独记录。
3. **结论跟随证据**：按观察→假设→验证推进。未能区分候选原因时记录“未确定”，再选择有价值的下一项观察。
4. **修复可追溯**：保留复现条件、关键输出、候选解释、修改与回归结果的对应关系；具体反查例子见 [调试的因果链](../dw-reference/references/method-integration.md#调试的因果链)。

## 中间态信号检查（Intermediate Signal Tracing）

中间态信号是管道内第一响应者，最终指标是滞后的——只盯最终指标会掩盖管道未激活或中间量失效。需区分：未执行（`enabled=0`）、未赋值/诊断遗漏、传参错误与契约允许的合法零值（详见 [信号演进与逐级闭环案例](references/signal-and-lifecycle-walkthrough.md)）。

```
□ 管道是否被调用？（入口日志/计数确认）
□ 输入是否正确？（检查输入内容与范围，而非仅看 shape/type）
□ 中间量是否合理？（范围、分布、趋势）
□ 输出是否被正确写回？（下游是否读取了预期字段）
□ 最终指标是否变化？
```

## 反向验证法（Reverse Verification）

顺序：**确定关键诊断信号 → 在每条返回路径写入诊断量 → 定义正常基准范围 → 运行并看信号输出 → 异常时追查具体层级**。不靠“看代码猜测它应该正确”。

**诊断变量设计**：所有返回路径（含提前 return 与异常分支）均写入诊断；使用可解释的物理量/比率并按时序记录；严格区分“未激活”和“激活后为零”。

---

## 闭环验证与全生命周期证据排查

验证按闭环执行：**定义预期 → 设置捕获点 → 运行 → 检查信号 → 异常时选择最能区分原因的节点 → 在已授权范围内修复 → 再运行**。

- **正反馈**（信号符合预期）：推进下游检查
- **负反馈**（信号偏离预期）：按证据定位边界，防止未解释偏差进入验收

沿数据链路优先观察最能区分假设的边界：

```
  输入创建 → 数据提取 → 合并/变换 → 质量过滤 → 核心算法 → 结果消费
      ↓          ↓          ↓          ↓          ↓          ↓
   类型正确?   提取量达标?  合并率正常?  过滤率合理?  输出符合预期? 下游可见?
```

1. **捕获点服务于假设**——在关键状态转换和边界插桩，避免无差别打印每一层。
2. **可观测性匹配风险**——长期审计信号进入正式遥测，一次性诊断只在复现期内保留。
3. **不因一次异常否定方案**——逐级排查案例见 [逐级闭环排查案例](references/signal-and-lifecycle-walkthrough.md#二逐级闭环排查案例输出全零案例)。

## 常见实现错误与管道未激活检查

当结果异常且尚无更强证据指向方案前提错误时，优先核对近期实现或集成缺陷：

| 类别 | 典型表现 | 检查方法 |
|------|---------|---------|
| 传参错误 | 参数被默认值覆盖、键名不匹配 | 逐层打印实际接收的参数值 |
| 索引/边界错误 | 越界、长度变化后索引失效 | 检查守卫条件 + 边界值测试 |
| 条件/逻辑错误 | `and`/`or` 混用、分支取反遗漏 | 分支覆盖测试 |
| 维度/类型错误 | shape 不匹配、精度隐式转换 | 打印 `.shape` + `.dtype` |
| 累积/状态错误 | 状态未在重置点清零 | 检查重置逻辑与状态生命周期 |
| 诊断遗漏 | 功能运行但诊断字段未赋值 | 搜索诊断输出字段的每个写入点 |
| 路径/配置错误 | 路径拼接、配置键名拼写 | 运行前打印配置解析结果 |

怀疑某段代码“未被执行”时，依次核对：**入口条件（guard/开关）→ 调用点存在性 → 参数逐层传递 → 返回值消费 → 诊断完整写入**，然后再评价方案效果。每次关键尝试的假设、改动与判决按需登记（示例见 [实验登记表格式](references/signal-and-lifecycle-walkthrough.md#三实验登记表格式示例)）。
