# 诊断与调试方法论

> 本 skill 是 [development-workflow](../development-workflow/SKILL.md) 的子模块，覆盖 **核心方法中的诊断与调试技术**。

---

## 按假设选择观测方法

| 当前问题 | 可区分假设的证据 | 详细方法 |
|----------|------------------|----------|
| 性能或资源瓶颈 | 代表性负载、热点、耗时和资源等待 | [dw-optimization](../dw-optimization/SKILL.md#性能分析流程) |
| 数值或业务结果偏差 | 相同输入下的结果、领域不变量、必要时的单变量对照或组件消融 | [dw-verification](../dw-verification/SKILL.md) |
| 管道未激活或信号异常 | 入口、输入、状态转换及下游消费证据 | 下文信号检查与链路排查 |
| 场景间表现不一致 | 受影响的代表性场景、边界和错误路径 | 按各场景预先定义的行为进行对照 |

先选择最能区分当前假设的观测点。工具按当前环境能力发现，诊断结果与最终验收结论分别记录。

---

## 隔离实验与证据记录

1. **最小独立复现**：隔离与故障相关的最少依赖；必要时绕过项目框架直接调用底层 API，规模以能复现且便于审查为准。
2. **对照条件明确**：每次尽量只改变一个待检验变量，保持其他输入、配置和环境可比；无法控制的差异单独记录。
3. **结论跟随证据**：按观察→假设→验证推进。未能区分候选原因时记录“未确定”，再选择有价值的下一项观察。
4. **修复可以追溯**：保留复现条件、关键输出、候选解释、修改与回归结果的对应关系，复用现有日志或实验记录。

## 中间态信号检查

实践中最容易犯的错误是只盯着最终指标，忽略了中间管道是否产生了正确的信号。

| 阶段 | 最终指标 | 中间态信号 | 候选解释与后续核实 |
|------|---------|-----------|-------------|
| 初版实现 | 无提升 | `feature_enabled=0/377(0%)` | 核对入口条件、配置和合格输入，确定为何未激活 |
| 第 2 版 | 无提升 | `feature_enabled=0`, `input_ready=0` | 核对输入条件与实际接收的参数，不能仅凭零值确定传参错误 |
| 第 3 版 | 无提升 | `feature_enabled=120/377(32%)`, `input_ready=205` | 已记录部分激活，继续核对零输出是否符合条件及下游是否正确消费 |
| 第 4 版 | 无提升 | 中间量全零且无错误日志 | 区分合法零值、未执行、未赋值和诊断遗漏 |

### 信号检查清单

```
□ 管道是否被调用？（增加 print/日志确认入口执行）
□ 输入是否正确？（检查输入数据内容，而非 shape/type）
□ 中间量是否合理？（范围、分布、趋势）
□ 输出是否被正确写回？（下游是否读取了预期字段）
□ 最终指标是否变化？
```

> **原则**：中间态信号是管道内第一响应者。最终指标是滞后的。优先检查信号，而非指标。

## 反向验证法：诊断先行

验证组件状态时，按这个顺序操作：**设置诊断变量 → 运行 → 查看诊断输出 → 根据输出判断组件是否正常运行**。

```
代码审查模式：
  代码是对的 → 代码应该产生 X 结果 → 运行验证 → 结果不对 → 重新审查代码
  （假设前提：你能通过看代码判断它是否正确）

反向验证模式：
  设置诊断变量 → 运行 → 看产出 →
    ├─ 结果显示预期信号 → 该捕获点符合当前预期，继续核对下游与目标行为
    └─ 结果显示异常信号 → 追查具体层级
  （不依赖对代码正确性的预判——让数据说话）
```

### 实施步骤

```
□ 步骤 1：确定关键诊断信号（什么中间量能直接反映组件是否在工作？）
□ 步骤 2：确保诊断代码完整（每个代码路径都要写入诊断变量）
□ 步骤 3：按需要用日志、断言或可视化呈现关键信号
□ 步骤 4：建立预期基准（不同场景下定义"正常"的中间量范围）
□ 步骤 5：迭代验证（改一次代码 → 跑诊断 → 看输出 → 确认行为符合预期）
```

### 诊断变量设计原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **每个路径都记录** | 函数的所有返回路径都必须设置诊断 | 提前 `return` 不写诊断变量 |
| **用值域可解释的量** | 用有物理意义的量（百分比、计数、比率） | 复杂的内部状态叠起来无法解读 |
| **时间序列优先** | 按时序记录，可以画折线图观察趋势 | 只输出均值会掩盖中间波动 |
| **区分"未激活"和"激活后为零"** | 用两个不同信号表示 | `enabled=0` vs `enabled=1, output=0` |
| **极端情况下也有输出** | 即使出错也记录错误原因 | 静默崩溃 → 下游不知道发生了什么 |

## 闭环验证

验证按闭环执行：**定义预期 → 设置捕获点 → 运行 → 检查信号 → 异常时选择最能区分原因的节点 → 在已授权范围内修复 → 再运行**。证据未区分假设时保留未确定状态。

### 两种反馈回路

| 回路 | 触发条件 | 响应 | 目的 |
|------|---------|------|------|
| **正反馈**（确认） | 信号在预期范围内 | 继续到下一阶段 | 保证进度向前 |
| **负反馈**（修正） | 信号偏离预期 | 按证据定位相关边界，必要时扩大链路检查 | 防止未解释偏差进入验收 |

**负反馈回路是质量的核心。** 发现异常 → 必须追溯到根因 → 修复 → 再运行确认。

---

### 与信号检查的区别

```
信号检查：      查找关键信号 → 确定异常区域 → 修复（目标：找到异常）
生命周期排查：  明确数据链路 → 每级捕获输入/输出 → 逐级验证
               └─ 逐级确认运行正常，再继续下一步
```

## 全生命周期证据排查

从数据管道的起点到终点建立可追踪证据；优先观察最能区分当前假设的边界，再按证据补齐相邻链路：

```
逐级验证顺序：
  输入创建 → 数据提取 → 合并/变换 → 质量过滤 → 核心算法 → 结果消费
      ↓          ↓          ↓          ↓          ↓          ↓
   类型正确?   提取量达标?  合并率正常?  过滤率合理?  输出符合预期? 下游可见?
```

关键原则：
1. **捕获点服务于假设**——在关键输入、状态转换和输出边界使用日志、断言、指标或调试器，避免无差别打印每一层
2. **可观测性匹配风险**——长期需要审计的信号进入正式遥测；一次性诊断只保留到结论可复现
3. **按预先定义的条件和基线判断“正常”，具体值随任务变化**

---

### 闭环排查示例

当中间信号异常时，不要在缺少证据时直接归因为“方案本身不适用”。一次真实案例中，输出全零被过早归因，导致链路中的多个实现缺陷未被发现。

正确流程：
```
输出全零 → 负反馈触发
  └─ 级 1：输入数据是否存在？→ 是（200+ 条）
  └─ 级 2：数据过滤掩码是否正确？→ 不对！新数据未过滤
      └─ bug 1：补数方法没更新掩码 → 修复
  └─ 再运行 → 输出有值但偏小
  └─ 级 3：统计字段存了什么？→ 子集数；总数另行统计
      └─ bug 2：赋值语义错误 → 修复
  └─ 再运行 → 输出正常
  └─ 级 4：状态标记 → 只有默认值
      └─ bug 3：回退路径没写标记 → 修复
  └─ 级 5：异常路径 → 4 条遗漏诊断
      └─ bug 4-6：补充赋值
  └─ 全部修复 → 验证通过
```

**核心教训**：最终指标异常时不要直接跳到「方案本身不适用」。从最接近近期改动、最容易观测和证伪的链路节点开始，逐级排查。

## 常见实现错误分类

**默认排查顺序**：当结果异常且没有更强证据时，可从以下顺序开始；证据指向其他层级时应调整，不把顺序当作概率结论：

```
优先级 1：近期实现或集成错误
   ├─ 传参错误（调用链中参数被默认值覆盖）
   ├─ 索引/边界错误（数组越界、守卫条件失效）
   ├─ 条件/逻辑错误（and/or 混用、分支条件写反）
   ├─ 维度/类型错误（shape 不匹配、float32 vs float64）
   ├─ 累积/状态错误（状态未在关键帧/重置点清零）
   └─ 诊断遗漏（功能实现了但诊断字段未赋值 → 输出全零）

优先级 2：方案理解偏差
   └─ 方案依赖的假设在当前场景是否成立？

优先级 3：方案本身不适用
    └─ 直接检查方案前提与反例；有明确证据时可先验证，不必穷尽其他层级
```

| 类别 | 典型表现 | 检查方法 |
|------|---------|---------|
| 传参错误 | 参数被默认值覆盖、参数名不匹配 | 逐层打印实际接收的参数值 |
| 索引/边界错误 | 数组越界、长度变化后索引失效 | 检查守卫条件 + 边界值测试 |
| 条件/逻辑错误 | `and`/`or` 混用、取反遗漏 | 分支覆盖测试 |
| 维度/类型错误 | shape 不匹配、float32 vs float64 | 打印 `.shape` + `.dtype` |
| 累积/状态错误 | 帧间状态未在重置点清零 | 检查重置逻辑 |
| 诊断遗漏 | 功能实现了但诊断字段未赋值 | 搜索诊断输出字段的每个写入点 |
| 路径/配置错误 | 路径拼接、配置键名拼写 | 运行前打印配置解析结果 |

## 管道未激活检查

当怀疑某段代码"没有被执行"时：

```
□ 入口条件是否满足？（if guard、配置开关、hasattr 检查）
□ 函数是否被显式调用？（搜索函数名是否存在调用点）
□ 参数是否被正确传递？（从调用链最外层逐层检查）
□ 返回值是否被接收或使用？
□ 诊断代码是否完整？
```

> 先用入口计数、调用路径和输出消费证据确认管道确实运行，再评价方案效果。

## 实验登记表

| # | 方向 | 假设 | 最小改动 | 实测指标 | 关键信号 | 判决 | 放弃原因 |
|---|------|------|---------|---------|---------|------|---------|
| 1 | 方案 A | 假设描述 | ~80 行 | 0.69 | enabled=32%, output=0 | ❌ | 方案未实际生效 |
| 2 | 方案 B | 假设描述 | ~30 行 | 0.68 | 信号噪声大 | ❌ | 输入质量不满足假设 |
| 5 | 方案 E | 假设描述 | ~3 行 | 0.69 | 本例受测范围内无退化 | 待验收 | 成本和副作用仍需相应证据 |

表中数字仅演示记录格式。实际记录需写明指标名称、单位、数据范围和条件；单个信号或无退化结果不能证明零开销或没有副作用。

**关键教训**：每次尝试都记录判决和理由。避免在 6 个月后回来发现有人又在试相同的方案。

## 版本回退策略

```
□ 先检查工作树和暂存区，识别用户已有修改；不得覆盖或混入无关改动
□ 用 `git show <commit> --stat` 和目标 diff 确认问题提交与回退粒度
□ 核对回退是否在现有授权的仓库、目标和操作范围内；新增或超范围动作再取得必要授权
□ 优先选择可审查、可恢复的方式：共享历史通常使用 `git revert <commit>`
□ 只恢复文件时，明确 source 与 path，并在执行前展示将被覆盖的差异
□ 禁止自动运行 `git reset --hard`、`git checkout -- <path>` 等覆盖型命令
□ 回退后运行针对性回归，并保留根因与判定证据
```
