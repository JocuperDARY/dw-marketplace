# 行为实现、数据完整性防护与分层测试闸门

> 本 skill 是 [development-workflow](../development-workflow/SKILL.md) 的子模块，覆盖 **行为实现、数据完整性防护与分层测试闸门**。遵循铁律 A1（可审计编辑）、B2（计划对照）、B4（适用闸门）、B5（数据完整性）。

## 行为变更的 TDD 实现

### RED-GREEN-REFACTOR 循环

```
  写失败测试(RED)
       │
       ▼
  确认测试因预期原因失败（非语法/导入错误）
       │
       ▼
  写最小实现(GREEN)
       │
       ▼
  确认所有测试通过
       │
       ▼
  重构(REFACTOR) —— 代码清晰化
       │
       ▼
  确认测试仍通过
```

### 测试分层策略

| 层级 | 范围 | 覆盖目标 |
|------|------|---------|
| **单元** | 最小行为单元 | 逻辑、边界、错误语义 |
| **契约/集成** | 模块、服务或外部接口边界 | 数据契约、状态转换、依赖协作 |
| **系统/硬件** | 真实运行环境 | 端到端数据流、兼容性、资源行为 |
| **冒烟** | 完整管线的代表性子集 | 关键路径可运行、产物格式正确 |

### 测试设计要求

- **先选最小充分层级**：能在低层验证的逻辑不依赖特定硬件/数据库/网络
- **测试数据匹配风险**：合成数据适合已知 ground truth；真实缺陷和兼容性仍需代表性样本
- **每层测试独立可运行**：硬件相关测试用标记隔离，无对应环境自动跳过
- **测试验证领域不变量**：只有当关键输出按契约不应全零/全空时才添加对应断言

TDD 适用于新增或改变可执行行为。纯文档、元数据和声明式配置先写能失败的结构/静态校验；无法自动化时记录人工验收步骤和原因。

### 实现纪律

1. 按当前计划逐项实现；若任务无需显式计划，不重复维护形式化 TODO
2. **手工修改使用运行时的可审计结构化编辑机制**（如 Edit 或 apply_patch）
3. 保护敏感信息（铁律 A2）
4. 实现过程中发现范围、风险或验收方式变化 → 先更新计划再继续

## 数据完整性防护

### 哨兵值策略

- 优先使用类型系统、可空字段或显式状态列表示"不适用/未测量"；只能用数值时才选择不会与合法值冲突的哨兵
- 数据收集端：未计算的指标不得伪装成合法测量值；是否允许 0 由领域契约决定
- 数据消费端：聚合前过滤哨兵值，每个图表面板检查"是否所有数据都是哨兵值"

### 元数据落盘

**运行时元数据**：对需要复现或比较的运行，在输出目录写入元数据文件，包含：

| 字段 | 用途 |
|------|------|
| 后端/引擎标识 | 下游根据后端类型做条件渲染 |
| 配置参数关键值 | 复现运行条件 |
| 代码版本哈希 | 追溯生成数据的代码版本 |
| 运行时间戳 | 区分多次运行 |

**用途**：下游分析脚本根据元数据做条件渲染（如"某类后端不显示特定指标"），不再靠猜测或启发式推断。

### 自检哨兵

在会生成决策性数据或报告的脚本输出阶段添加与领域不变量匹配的自检。分两级：

**FAIL 级（硬阻断）—— 必须包含的检查**：

| 检查项 | 含义 |
|--------|------|
| 关键字段是否违反领域不变量 | 例如本应有信号的流场幅度全零 |
| 关键字段是否全程为哨兵值 | 如诊断字段全为 -1 → 旧代码产物 |
| 数据行数是否为零 | 如所有输入文件为空 → 数据收集失败 |

**WARN 级（软提示）—— 建议包含的检查**：

| 检查项 | 含义 |
|--------|------|
| 子分类合计与总数不一致 | 数据聚合逻辑可能有误 |
| 均值/中位数比过大 | 偏态严重，需关注 |
| 某类字段全部可用或全部不可用 | 可能是过滤条件过于激进 |

## 分层测试闸门

代码变更完成后，先根据变更类型和风险选择适用闸门，再进入验证阶段。仓库已有的标准命令优先；不要为满足清单临时引入新工具。

### 闸门检查清单

| 闸门 | 何时适用 | 通过标准 |
|------|----------|---------|
| 行为/回归测试 | 可执行行为发生变化 | 相关测试通过，失败基线已被正确捕获 |
| 集成/硬件测试 | 依赖边界、真实硬件或完整管线受影响 | 通过；若环境缺失，记录跳过原因与残余风险 |
| 格式/风格检查 | 仓库已配置相应工具 | 无新增违规 |
| 类型/构建检查 | 类型、编译或打包边界受影响 | 无新增错误 |
| 代码审查 | 所有非平凡代码变更 | 无阻断性正确性问题 |
| 安全检查 | 认证、权限、输入、文件、网络、秘密或依赖受影响 | 无未处置的高风险问题 |
| 结构/链接校验 | 文档、配置、元数据或 Skill 变更 | 结构、引用和约束检查通过 |

### 闸门失败处理

| 级别 | 含义 | 行动 |
|------|------|------|
| **致命** | 安全漏洞、数据丢失风险 | **阻断**——必须修复后才能继续 |
| **高危** | Bug 或显著质量问题 | **警告**——应在当前阶段修复 |
| **中危** | 可维护性问题 | **记录**——可在下一阶段修复或记录为技术债 |
| **低危** | 风格或次要建议 | **备注**——可选修复 |

> 同一闸门反复失败且证据不再增加时，停止盲目重试，回到根因和方案假设；次数不是唯一判据。

## 实现阶段反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 行为变更先写实现后补测试 | 测试覆盖不完整、偏误 | 先写测试并确认因预期行为缺失而失败，再写实现 |
| 修复症状不修根因 | 问题会以新形式复发 | 追到数据流/控制流的源头 |
| 同时改多个不相关的东西 | 无法隔离是哪个改动生效 | 一个变更单元只修一个根因 |
| 忽略哨兵值设计 | 0 和"未测量"无法区分 | 定义明确的哨兵值并全链路遵守 |
| 凭感觉验证 | "看起来好了"、"好像快了" | 保留基线，记录量化指标 |
| 一次改太多 | 不相关改动混在同一变更单元 | 按可独立理解和验证的目的拆分 |
| 无 profiling 盲目优化 | 优化了占比 <5% 的代码，净收益微乎其微 | 先用性能分析工具定位热点，再看决策树 |
| 优化后跳过功能等价验证 | "改了几行而已不用测" | L1→L2→L3 逐级验证 |
| 过早优化非热点 | 核心功能未完成就开始优化 | 先正确运行，再用 profiling 找瓶颈 |
| 优化后接口不兼容 | 改了函数签名或返回值类型 | 优化前后接口保持一致 |
| 过度复杂的优化 | 为有限收益引入大量晦涩代码 | 权衡可复现收益与复杂度，必要时放弃微优化 |
| 优化后移除原注释 | 优化完删掉原有注释和文档 | 保留注释，必要时增加优化说明 |
| 只测单一规模 | 忽略固定开销、扩展性或边界 | 选择能代表实际风险的规模与边界样本 |
