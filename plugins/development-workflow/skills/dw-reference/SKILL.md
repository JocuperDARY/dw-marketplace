## 场景化快速参考

不同改动类型可以裁剪阶段；所有任务都保留目标、风险、证据和自有资源清理：

| 改动类型 | 最低证据 | 风险升高时扩展 |
|---------|---------|---------------|
| **Bug 修复** | 可复现失败 + 根因证据 + 回归测试 | 集成/端到端、回滚或事故 containment |
| **性能优化** | 同口径本地基线 + 功能等价 + 代表性 workload | 容量、长稳、资源和多环境验证 |
| **新功能/模块** | 明确契约 + 失败测试/验收用例 + 集成证据 | 多方案取舍、安全与迁移审查 |
| **重构** | 行为特征测试 + 构建/回归 | 跨模块契约与性能退化预算 |
| **参数调优** | 预先定义目标 + 同口径对照 | 多场景、方差、消融与回退 |
| **配置变更** | 解析/schema + 受影响主路径 | 权限、部署、兼容与回退演练 |
| **纯文档/注释** | 结构/链接/示例检查 + diff 审查 | 发布文档或可执行示例的端到端验证 |

### Bug 修复 — 快速流程

```
□ 诊断：收集多维度证据 → 建立假设 → 确认根因
□ 写背景分析（原因 + 现象）
□ 构造最小复现用例
□ 编写与风险匹配的精简操作指引
□ TDD 实现（先写复现测试 RED → 修复 GREEN → 重构）
□ 功能验证（断言或对比输出）
□ 运行适用的质量闸门
□ 按影响面执行集成验证，确认不引入 regression
□ 仅在仓库惯例、用户要求或后续维护确有价值时同步文档或知识
```

### 性能优化 — 快速流程

```
□ 记录基线指标（FPS / 内存 / 精度）
□ 有真实取舍时比较可行方案
□ 使用当前运行时的结构化编辑机制实现（Edit/apply_patch 等）
□ 量化验证（与基线同口径对比）
□ 功能等价验证（L1→L2→L3）
□ 按仓库惯例和维护价值决定是否同步工作历史
```

### 新功能 — 完整流程

```
□ 写与风险匹配的计划；存在真实取舍时比较方案
□ 高风险或关键歧义处评审
□ 逐项实现计划，行为变更走 TDD
□ 涉及数据时按契约设置缺失状态与不变量
□ 运行适用的分层质量闸门
□ 运行仓库原生构建/结构验证
□ 功能验证（每步验收标准）
□ 集成验证
□ 三 C 判定（一致性 + 完整性 + 正确性）
□ 非平凡或高风险变更执行独立 Code Review
□ 按仓库惯例、用户要求和维护价值决定是否同步文档或知识
```

## 检查清单

### 标准检查（按适用性）

```
□ 仓库原生构建/结构检查通过
□ 受影响的主路径与关键边界有新鲜证据
□ 性能/容量声明有同口径基线；其他声明有明确验收证据
□ 手工修改通过运行时的可审计结构化编辑机制完成
□ 敏感信息未泄露
□ 计划深度与风险匹配；范围变化已同步
□ 重要文件的增删已按 B6 留痕（含被删内容完整原文与耐久落点）；关键文件变更已取得一致通过的审批
□ 涉及数据时，缺失状态和失败不变量已定义
□ 所有适用测试闸门已通过；未验证项与残余风险已记录
□ 三 C 验证已通过
□ 仅在行为/契约变化或仓库要求时更新既有文档
□ 本任务启动的子进程、开发服务器和临时资源已回收并确认
```

### 三 C 判定清单

```
一致性：
□ 实现与操作指引中的方案一致
□ 无"惊喜"逻辑（指引未讨论的实现）
□ 参数/配置与设计一致

完整性：
□ TODO list 全部实现
□ 边界情况已处理
□ 错误处理已覆盖
□ 配套产出齐全（注释/文档/配置/诊断）
□ 回退/关闭机制存在

正确性：
□ 编译/导入通过
□ 功能验证通过
□ 集成验证通过
□ 量化指标在预期范围内
```

### 诊断检查清单

```
□ 多维度证据已收集（数据输出/可视化/日志/配置/数据流/API文档）
□ 每个候选根因有明确假设和证据
□ 根因层级已分类（致命/严重/数据陈旧/呈现缺陷）
□ 修复优先级已确定
□ 未跳级归因（实现错误 → 方案偏差 → 方案不适用）
```

## 反模式清单

### 规划阶段

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 没有目标/风险/验收就写代码 | 方向性错误、返工 | 先写与风险匹配的计划 |
| 计划太粗 | 遗漏关键步骤、无法对照检查 | 分解到可独立验证和回退的粒度 |
| 计划不考虑回退 | 失败时无法恢复 | 每阶段前备份，冒烟先行 |
| 计划不写验收标准 | 不知道何时算完成 | 每个子步骤必须有可量化验证产出 |
| 跳过诊断直接修 | 治标不治本，问题复发 | 先确认根因再动手 |

### 实现阶段

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 先写实现后补测试 | 测试覆盖不完整、偏误 | TDD：先写测试确认失败，再写实现 |
| 修复症状不修根因 | 问题会以新形式复发 | 追到数据流/控制流的源头 |
| 同时改多个不相关的东西 | 无法隔离是哪个改动生效 | 一个变更单元只修一个根因 |
| 忽略哨兵值设计 | 0 和"未测量"无法区分 | 定义明确的哨兵值并全链路遵守 |
| 凭感觉验证 | "看起来好了"、"好像快了" | 保留基线，记录量化指标 |
| 一次改太多 | 不相关目的混在同一变更单元 | 按可独立理解和验证的目的拆分 |
| 无 profiling 盲目优化 | 没有证据证明目标路径重要 | 先定位对目标指标有实质影响的热点 |
| 优化后跳过功能等价验证 | "改了几行而已不用测" | 按风险选择单元、集成和回归等价证据 |
| 过早优化非热点 | 核心功能未完成就开始优化 | 先正确运行，再用 profiling 找瓶颈 |
| 优化后接口不兼容 | 改了函数签名或返回值类型 | 优化前后接口保持一致 |
| 过度复杂的优化 | 为有限收益引入大量晦涩代码 | 权衡可复现收益与复杂度 |
| 优化后移除原注释 | 优化完删掉原有注释和文档 | 保留注释，必要时增加优化说明 |
| 只测单一规模 | 忽略固定开销、扩展性或边界 | 选择代表实际风险的规模和边界样本 |

### 验证阶段

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 测试通过了就认为没问题 | 测试可能覆盖不足或阈值太宽 | 按领域契约覆盖能区分正确与错误的关键不变量 |
| 只看代码不看输出文件 | 代码逻辑正确但数据流有问题 | 验证输出文件中的实际值 |
| 跳过特定硬件测试 | 硬件相关的 bug 未被发现 | 无对应硬件环境用纯函数测试覆盖核心逻辑 |
| 验证完不汇总偏差报告 | 遗漏的步骤被遗忘 | 逐项对照计划生成偏差清单并分级 |
| 跳跃式排查 | 结果异常 → 直接怀疑方案不行 | 按归因优先级逐级排查（P1→P2→P3） |
| 跳过三 C | 改完"看起来跑通"就提交 | 三 C 是落地最低门槛 |
| 忽视边界 | 只测主路径 | 按风险覆盖受影响的关键边界和错误路径 |

### 收尾阶段

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 需要长期维护的契约变化未同步文档 | 后续维护者不知道为何这样设计 | 更新最接近该契约的现有文档 |
| 可复用结论只留在临时对话 | 下次会话从零开始 | 更新合适的仓库文档；外部知识库需可用且获授权 |
| 自动提交代码 | 操作者不知道改了什么 | 提交前呈交操作者审批 |
| 不记录基线对比 | 无法证明改动有效 | 记录足以支持当前声明的关键指标和同口径对比 |
| 留下开发服务器或子进程 | 占用端口与资源 | 仅按所有权记录回收本任务资源并验证退出 |

## 附录 A：合成测试数据设计原则

1. **Oracle 可解释**：优先使用解析解、独立实现或明确领域不变量，不把被测算法自身输出当真值
2. **变换覆盖风险**：从最简单可判定案例开始，再加入真实会触发缺陷的复杂度
3. **输入满足前置条件**：同时覆盖有效、边界和无效输入，避免只生成算法最擅长的数据
4. **可复现随机**：记录种子、生成器版本和关键参数
5. **容差预先定义**：按数值尺度和业务误差预算设定，不在看到结果后放宽

## 附录 B：GPU 计算开发专项注意事项

1. **异步边界**：仅在主机读取结果、跨流依赖或性能计时边界做必要同步，避免逐操作同步破坏并行性
2. **缓冲区契约**：验证 shape、dtype、布局、设备和生命周期与 API 约定一致
3. **计算方向约定**：对输入/参考方向、坐标系和符号约定做可判定对照测试
4. **数值表示**：定点缩放、精度、溢出和舍入策略必须进入测试边界
5. **领域不变量**：只在契约要求时断言非全零；同时覆盖合法全零、空输入和不适用状态
