# 任务交接（Handoff）

> 本 skill 是 [development-workflow](../development-workflow/SKILL.md) 的子模块，覆盖 **任务全程重新审视、参考内容盘点、增删对账与接手文档产出**。把铁律 B2（TODO 与计划严格对照）延伸到跨会话交接，并遵循 A2（敏感信息脱敏）与 A3（交接不代替授权）。

---

## 核心原则

1. **交接文档是重新审视，不是对话摘要。** 必须回到任务起点，用证据重建"目标 → 起点 → 过程与效果 → 结果 → 后续"的完整链条，而不是按时间顺序复述聊天记录。
2. **TODO 对账表是严谨参照。** 先从对话与计划中重建任务清单，逐项对账状态与证据；对账表不完整时，交接文档不成立。
3. **增删如实记录，像 commit 一样可核对。** 新增、修改、删除、重命名、回滚、放弃都列出对象、原因与当前状态；被否决或被放弃的项不得静默消失。
4. **结论按证据分级。** 完成、部分、未开始、阻塞、放弃、未验证必须分开；没有证据的"应该没问题"只能写为未验证，并注明缺哪个检查。
5. **只引用，不复制。** 已在 spec、计划、ADR/决策记录、issue/工单、commit、diff 或日志中的内容，用路径或 URL 引用，不重复粘贴。
6. **交接描述已发生与建议，不产生新授权。** 未来计划与已获授权严格分离；已消耗的授权额度、仍需重新申请的许可、禁止操作都必须写入文档。
7. **参考内容要逐一盘点。** 任务中加载过的文档、网页、记忆、计划与未完成目标都要列入清单，并按过往引用频率分组排序；只记录位置与用途，不复制内容。

---

## 重新审视四问

写作前逐条回答；任何一项答不上来，先补齐证据再写：

| 问题 | 必须回答的内容 |
|------|----------------|
| 最初的目标是什么 | 用户原始诉求（尽量用原话）、验收标准，以及中途追加或变更的要求 |
| 从什么起点开始 | 仓库/路径、分支与起始 commit、工作树与环境状态、当时已知的阻塞 |
| 做了什么、效果如何 | 每个任务项的动作、证据（命令/输出/文件）与实测效果；失败的尝试同样记录 |
| 最后的结果怎么样 | 对照目标逐项判定：达成 / 部分 / 未达成 / 未验证；残余风险与已知缺陷 |
| 未来计划做什么 | 未完成项按优先级排成下一步 TODO，注明前置条件、验证方式与所需授权 |

## 任务清单（TODO）对账规则

- 存在显式计划/操作指引时，按其条目编号逐项引用（写明文件路径）；没有时按对话重建，并标注来源（用户第 N 条要求 / 评审意见 / 计划外新增）。
- 每项一行，给出状态标记与证据指针；状态不明确时标为"未确认"，不得默认完成。
- 计划外的顺手动作（额外修复、清理）也要列出；被修订、否决或撤回的要求、以及放弃项都要保留对账行，并注明处置原因与时间。
- 对账表与"未来计划"必须闭合：未完成项要么进入未来计划，要么显式标记为放弃/移交。
- 状态与证据按下表对齐，不混用含义：

| 状态 | 含义 | 证据要求 |
|------|------|----------|
| ✅ 完成 | 已达成且有证据 | 命令/输出/文件路径/commit |
| 🚧 部分 | 只完成一部分 | 已完成范围 + 缺口 |
| ⬜ 未开始 | 计划内但未动 | 前置条件 |
| ⛔ 阻塞 | 外部原因无法推进（HOLD） | 阻塞原因 + 解除条件 |
| ❔ 未验证 | 动作已做但验证缺失（UNVERIFIED） | 缺失的检查项 |
| 🗑️ 放弃 | 已决定不做 | 决策时间与原因 |

对跨平台发布证据另用以下机器可读状态，不能互相折叠：

| 证据状态 | 含义 |
|----------|------|
| `IMPLEMENTED` | 已写入实现，但尚未完成对应验证 |
| `PASS_STATIC` | 静态结构/身份检查通过 |
| `PASS_FOCUSED` | 指定焦点测试通过 |
| `VERIFIED` | 运行时和独立读回均通过 |
| `VERIFIED_DEGRADED` | 已验证但明确存在受限能力 |
| `UNVERIFIED` | 已执行或已计划，但缺少所需独立证据 |
| `NOT_RUN` | 前置条件、授权或平台不适用而未运行 |
| `FAIL` / `HOLD` | 失败或安全门槛未满足，必须保留原因 |

## 增删清单（对照 commit / diff）

| 操作 | 对象 | 说明 | 状态 |
|------|------|------|------|
| 新增 / 修改 / 删除 / 重命名 / 回滚 / 放弃 | 文件路径、符号、决策或资源 | 为什么改、影响面 | 已提交（SHA）/ 工作树未提交 / 已回滚 |

- 文件变更给到路径级；决策变更（采纳/放弃的方案）单列理由与重估条件。
- 工作树中未提交的改动必须点名，接手者据此决定保护还是继续。

## 参考内容清单（加载与引用重审）

任务过程中加载或引用过的材料必须逐一列出，并按过往的提及、使用、参考频率分组排序——接手者据此知道哪些是权威依据、哪些只是顺带看过：

- 至少覆盖以下五类（出现其他形态的材料按同样格式登记）：**本地文档**（spec、设计、README、rules、日志、证据文件）、**网页链接**（URL、外部资料）、**上下文记忆**（memory 文件、规则上下文、前序会话记录、旧交接文档）、**编写好的计划**（计划/操作指引文件）、**尚未完成的目标**（未达成目标、暂缓项、开放问题）。
- 每条一行记录：类型 | 位置（路径或 URL） | 用途（为什么参考） | 引用频次 | 分组 | 状态。
- 频次按对话中的提及/打开/使用次数计数；难以精确计数时标注"多/中/单次"并说明依据，无法确认的写"未确认"，不得臆断。
- 覆盖规则：即使只引用一次，但承载验收标准、契约、授权或关键决策的材料，一律归入高组并注明原因。
- 状态标注：仍有效 / 已失效或被取代（注明替代物）/ 待复核。
- 链接与记忆条目只写位置与用途，不复制内容；带凭据或签名参数的 URL 先脱敏。
- 未完成目标按"目标 → 当前状态 → 阻塞或前置条件 → 建议动作"记录；它与 TODO 对账表的未完成项分工不同：目标是方向与授权，TODO 是执行项。

| 分组 | 判据 | 处理建议 |
|------|------|----------|
| 高 | 反复引用，或承载验收/契约/授权/关键决策 | 接手者开工前先通读 |
| 中 | 多次参考、支撑局部结论 | 用到时再读 |
| 低 | 一次提及或背景参考 | 仅留索引，不必优先读 |

## 1. 原始目标
- 原始诉求（原话）：
- 验收标准：
- 中途追加/变更的要求：

## 2. 起点
- 路径 / 分支 / 起始 commit：
- 工作树与资源状态：
- 当时已知阻塞：

## 3. 执行与效果（TODO 对账）
- 任务项 | 来源 | 状态 | 证据 | 效果与备注

## 4. 变更增删
- 操作 | 对象 | 说明 | 状态

## 5. 参考内容清单（按引用频率分组）
- 高：类型 | 位置 | 用途 | 频次 | 状态
- 中：…
- 低：…
- 未完成目标：目标 | 状态 | 阻塞/前置 | 建议动作

## 6. 最终结果
- 对照目标逐项判定：
- 当前产物与验证等级：

## 7. 未来计划（下一步 TODO，按优先级）

## 8. 接手必读
- 关键文件与入口：
- 复现 / 验证命令：

- 禁止操作：未经用户授权的提交、推送、部署、删除、外部状态变更

## 保存与交付

- 默认保存到操作系统临时目录（Windows `%TEMP%`、类 Unix `$TMPDIR` 或 `/tmp`），文件名 `dw-handoff-<yyyyMMdd-HHmm>-<slug>.md`；用户指定位置时从其指定。
- 文档不进工作树、不提交、不推送，除非用户明确要求。
- 完成后向用户报告：文件绝对路径、一句话摘要、仍需用户决定的事项。
- 用户说明了下一个会话的用途或重点时，按其焦点裁剪文档（突出相关 TODO、文件与授权）。

---

## 交付与发送证据

- 将文件保存到 `%TEMP%` 或其他路径，只能证明文件已经写入该路径，不能证明交接已经送达下一个会话或其他 Agent。
- 跨任务交接只有在目标端实际收到并返回发送回执后，才记录为“已交付”；回执至少包含目标标识、发送时间、结果状态和目标端可读取的工件路径。
- 如果宿主 Guard 或发送工具阻止交付，状态必须写为“交付阻塞”，同时提供完整可复制的交接提示、工件绝对路径、阻塞原因和重新发送所需的授权/前置条件；不得把临时文件路径写成发送成功。
- 发送失败、超时、未知和未运行都保留在结果与 TODO 对账中，不用“文件已生成”替代发送结果。
## 完成前检查清单

```text
□ 四问（目标/起点/过程与效果/结果/未来计划）均已用证据回答
□ TODO 对账表覆盖对话中每一条明确要求，并与未来计划闭合
□ 增删清单完整，未提交改动已点名
□ 未验证 / 阻塞 / 放弃项显式标注，未伪装成完成
□ 已存在工件用路径引用，未重复复制内容
□ 参考内容清单覆盖本地文档/网页链接/上下文记忆/计划/未完成目标五类
□ 清单按引用频率分组；低频但承载验收/契约的材料已注明提升理由
□ 链接与记忆只记位置与用途（带凭据参数已脱敏），未完成目标单列
□ 授权额度（已消耗/仍有效）与禁止操作已写明
□ 关键进程、临时目录、端口、锁的状态与清理责任已写明
□ 已列出建议技能
□ 敏感信息已脱敏（密钥、口令、个人信息）
□ 保存位置与路径已报告给用户
```

## 反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 按时间顺序复述对话 | 接手者无法重建目标与结论 | 按四问重审后再写 |
| 未完成项从 TODO 中消失 | 造成"已完成"错觉 | 保留并标注未开始/阻塞/放弃 |
| 未验证写成完成 | 接手者误信结论 | 按证据分级，注明缺失检查 |
| 重复粘贴 spec/commit 内容 | 文档臃肿且容易与事实脱节 | 用路径或 URL 引用 |
| 把未来计划写成已授权任务 | 越权执行 | 计划与授权分离，写明需重新申请 |
| 交接文档写入工作树并提交 | 污染仓库历史 | 默认放系统临时目录，除非用户指定 |
| 省略未提交改动与脏资源 | 接手者误用或破坏现场 | 点名工作树 diff、进程与临时目录 |
| 参考内容只列文件，漏掉网页、记忆、计划与未完成目标 | 接手者找不到关键依据 | 五类材料全部盘点 |
| 按感觉排序、不数引用频次 | 权威资料被埋没，噪音被高估 | 按提及/使用次数分档，验收类材料强制进高组 |
| 内联带凭据的链接或复制资料全文 | 泄密，文档臃肿且易过期 | 只记位置与用途，先脱敏 |
