## 概述

在系统优化与功能开发中，每一次代码改动都是对既有系统的扰动。本 skill 的目标是在「快速迭代」和「系统稳定性」之间建立硬约束——用可量化的验证替代直觉判断，用结构化的流程降低回溯成本。

**核心信念**：
- 「看起来对了」是 bug 的温床 —— **没有量化的验证等于没有验证**。
- 「先动手再说」是返工的起点 —— **先明确目标、风险和验收证据，再选择与影响面匹配的流程**。
- 「肯定是环境/方案/库的问题」是排查的天敌 —— **从最接近改动且最容易证伪的假设开始，不用未经验证的概率替代证据**。

本方法论提炼自真实项目的完整开发-调试-验证-维护循环，面向 AI 编码助手协作场景，泛化至任何语言/框架/项目类型。

## 铁律体系

铁律分为两类：**工具使用铁律**（编辑纪律与安全）和 **流程铁律**（过程纪律）。

### 一、工具使用铁律

```
铁律 A1：手工修改必须使用当前运行时提供的可审计结构化编辑机制。
         —— Claude Code 使用 Edit/Write，Codex 使用 apply_patch；格式化器、代码生成器
         等确定性批量工具可按项目惯例执行。创建、移动和删除前确认目标路径与作用域，
         不用跨 shell 拼接路径执行破坏性操作。

铁律 A2：保护敏感隐私信息，不得以任何形式泄露。
         —— MCP 调用前检查参数是否含凭据；不打印完整 Key；
         不上传项目数据到未授权第三方。

铁律 A3：Agent 不得自行执行 git commit。
         —— 所有 commit 由用户亲自审核后执行。Agent 只能在用户明确授意下
         准备 commit 内容（staged files + message），不得绕过用户直接提交。
         例外：用户口头授权的一次性 commit（如 "commit this"）不在此限。

铁律 A4：按任务需要发现并选择工具，不假定某个 plugin、MCP、skill 或 agent 存在。
         —— 工具的价值是减少不确定性或提供更可靠的执行能力；调用数量本身不是目标。

         执行细则：
         a) 先看已声明能力，再按当前步骤选择最小充分工具集；不得凭记忆猜测可用性。
         b) 专用工具能显著提高正确性、速度或可追溯性时调用；否则使用仓库已有工具链。
         c) CodeGraph 仅在仓库存在 `.codegraph/` 时优先使用；不存在时直接回退到 `rg`
            和文件读取，不自行创建索引。
         d) 多工具重叠时的决策：
            · 常规任务：选择最适配的一个
            · 关键任务（安全/架构/跨模块）：启动多个工具并行审查，综合决策
            · 不确定时：先做低成本只读检查，再决定是否扩大工具集合
```

### 二、流程铁律

```
铁律 B1：计划先行，执行在后。
         —— 开始实现前至少明确目标、影响面、步骤和验收证据。跨模块、高风险、
         不可逆或存在关键取舍的变更写成操作指引；窄小且可逆的变更可用简短计划。
         只有缺失的决策会改变范围、风险或外部状态时，才需要暂停等待用户确认。

铁律 B2：TODO 与计划严格对照。
         —— 有显式计划时，TODO、实施和验证证据必须能对应；执行中发现范围变化，
         先更新计划。简单任务无需为了形式重复维护两份等价清单。

铁律 B3：发现偏差立即分级修复。
         —— 每完成一步即与计划对照；偏差按严重度（P0/P1/P2/P3）分级。
         修复流程：先读计划→理解→修复方法论→实施→再读计划→验证。

铁律 B4：所有代码变更必须过测试闸门。
         —— 先根据变更类型、风险和仓库能力选择适用闸门：行为变更走失败测试→实现→
         回归；文档/配置走结构或静态校验；安全敏感和跨模块变更扩大审查范围。
         所有适用闸门通过后才进入下一阶段；无法运行的闸门必须说明原因与残余风险。

铁律 B5：保护数据完整性。
         —— 数据处理变更必须区分缺失、不适用与合法零值，并定义与领域契约一致的
         不变量和失败条件。只有在"关键字段不应全零"确为业务不变量时才硬阻断。

铁律 B6：重要文件的增删必须留痕、旧版本保留、关键文件先审批。
         —— 对重要文件（影响后续方向的重要节点文件、系统框架中的核心代码与核心逻辑、
         技能/规则/契约文件等；没有耐久备份的是风险加重项）增删内容前：完整记录删除
         的内容与新增的内容及各自理由；在明确确认旧版本已失去全部价值、仅剩占用空间
         之前，不得移除旧版本；"高度重要、极其关键"的增删先取得一致通过的审批
         （2–4 个子 agent 交叉审议，或按无子 agent 的备选方案执行）后才能修改。
         细则见《重要文件增删治理》。
```

## 重要文件增删治理（留痕 / 版本保留 / 审批）

**适用对象**：重要文件——① 影响后续方向的重要节点文件（计划、决策、契约、基线配置、路线文档）；② 系统框架中的核心代码与核心逻辑（总纲、规则、钩子、入口、关键算法与状态机）；③ 技能、规范与模板正文。

**"没有备份"的判定**：旧内容无法从耐久位置（提交历史、归档、副本）恢复即为没有备份。这是风险加重项，不是适用前提；对这类文件，删除任何内容前必须先保留被删内容原文（见第 1 条）。

**"高度重要、极其关键"的判定**：判定项——① 不可逆或回滚代价高；② 改变既有可观察契约或已批准行为（接口、schema、规则选择、路由结果等）；③ 跨项目或长期影响；④ 涉及安全或数据完整性；⑤ 没有独立备份。

- **关键（全量审批）**：含 ① 或 ④，或包含对既有已批准内容的删除/替换，或判定不明。
- **常规（留痕 + 通知用户，不触发全量审批）**：仅含 ②③⑤ 且为追加性、可逆、不改变既有可观察行为。
- **示例**——关键：删除或替换总纲铁律、修改状态机或安全校验语义、删除既有路由/规则选择结果、移除旧版本文件；常规：新增不影响既有路径的路由 pattern、补充测试断言、不改变语义的措辞修正。
- 降级判断必须写明依据。

不改变语义与行为的编辑（错别字、格式、链接修复）不受本审批约束，但仍必须使用可审计编辑并留下可核对的变更痕迹。

### 1. 增删留痕

| 操作 | 必须完整记录 | 必须说明的理由 |
|------|--------------|----------------|
| 删除 | 被删内容原文（或原文快照）、位置、影响面 | 为什么必须删；替代物或替代方案；保留会怎样 |
| 新增 | 实际写入的完整内容、位置 | 解决什么问题；依据（需求/证据/决策） |
| 替换/修改 | 改动前后对照（old → new） | 为什么改；旧内容为何不再成立 |

- 记录必须能与 diff / commit 对照核对，不能只写"优化了 X""清理了旧内容"。
- 没有备份的文件删除任何内容前，必须先记录被删内容原文——记录本身就是回溯与修复依据。
- 耐久落点：仓库内变更记录、版本记录、归档目录（附 SHA-256）或提交信息（提交信息仅在用户执行提交时适用；Agent 不得自行提交——铁律 A3）；交接文档与临时位置（`%TEMP%`、`.tmp`）只能作辅助，不能作为唯一落点。
- 记录必须绑定实施前的基线哈希；实施后按实际写入结果**追加**定稿，不回改已写入条目。

### 2. 旧版本保留

- 旧版本文件、旧规则、旧实现与历史归档默认全部保留。
- 只有"明确确认旧版本已失去全部价值与存在意义、仅剩占用空间"时才允许移除；移除前记录确认依据与审批结果。
- 资源清理只针对本任务创建且路径已确认安全的临时资源；历史版本与治理证据（审批记录、基线快照）不纳入清理。

### 3. 关键文件审批

对"高度重要、极其关键"的增删，先取得一致通过，再修改。

**路径 A —— 可调用子 agent 时**

1. 由 2–4 个子 agent 对拟增删内容分别 debate 与 verify，覆盖不同视角（需求忠实性、集成一致性、对抗风险）；评审数量按运行时并发上限编排，可分批或串行，不得因槽位不足跳过。
2. 只统计「有效结论」：每份结论以固定格式给出 VERDICT 与 REASONS，并引用所评文本的版本标识或内容哈希；未引用现行版本/哈希的结论记为 INVALID（不计同意、不计反对）并重新索取，再次失败按不可用处理。结论收到后立即写入耐久变更记录（绑定所评文本哈希与时序），先于任何修改完成；记录只追加、不回改已封存条目。有效结论不足 2 份需转路径 B 时，必须在耐久记录中显式记因并通知用户；若 ≥2 名已启动评审者返回 INVALID（而非未完成），必须走 B1（用户审核），禁止降级 B2。
3. 全部同意 → 允许修改；修改后按第 1 条留痕。
4. 存在反对 → 收集拒绝理由 → 整理意见并决定是否采纳 → 理解、审核采纳的意见 → 修订后全量重新提交审批（不只审差量），直至一致通过；无法消解的分歧按未通过处理（HOLD），并按 B1 形式提交用户（拟增删内容、分歧点、候选取舍、解除条件）。
5. 实施超出已获批文本范围 → 重新审批；纯执行偏差按铁律 B3 处理。

**路径 B —— 无子 agent 方案时**（通过要求与路径 A 一致）

- B1（最稳妥）：中断任务流程，输出信息充分的提示词（拟增删内容、理由、风险、候选取舍），由用户在**新对话**中审核；未经该审核不得修改。
- B2（用户无法持续关注时）：不借助子 agent 与新任务，自行审核，并将审核重复 2–4 次；每次更换思维链与思考方向（例如：需求忠实性 → 结构影响 → 反例与风险 → 可执行性）。每轮记录角度、实际检查项、发现与结论；"零发现"轮必须列出实际检查项，不得形式化通过；轮次间出现分歧时按路径 A 第 4 条闭环处置。

**紧急场景**：铁律 B6 不豁免。未触碰受审文件本体的遏制、备份与止损动作可以并行，同时立即启动审议或按 B1 送审；恢复到最近一次已获批版本（不改写受审内容、不混入新改动）属于止损动作，可在耐久记录登记并通知用户后先行执行，随后补审。

**审批记录**：参与方（子 agent 标识或自审轮次）、评审角度、是否同源、各自结论、反对意见与处置、最终结论，与增删留痕一并保存；一致通过是覆盖性门槛，不代表独立错误过程已被证伪。

## 对外表达与建议方式

所有子 skill 共用以下表达方式：围绕读者当前需要理解或执行的事，使用具体事实、清楚的条件和可执行的下一步。

提出建议时，先说明推荐怎么做，以及这样做能解决什么问题；涉及选择时，补充影响决定的条件和取舍。汇报进度、交接或审查结论时，先说明当前事实和证据支持的结论，再说明尚待确认的部分与下一步。常规状态与交接优先陈述本轮范围、已完成事项、当前可核验状态和下一步；涉及保持原状的内容时，说明核对结果及其覆盖范围。篇幅按任务需要安排，简短说明也可以完整表达。

一般性提醒优先写成具体做法、适用条件和预期作用。例如：“先核对当前输入与目标范围，再执行已授权的修改，最后用对应检查确认结果。”证据不足时，说明当前可以确认什么、还需要什么证据，例如：“目前只完成了少量训练更新，模型是否更善于识别推导错误，还需要通过独立评测确认。”

当现有授权、受保护范围、安全或资源条件、证据门槛、预算上限或已确认失败确实限制当前动作或结论时，明确说明受限内容和原因；需要暂停时，指出具体停在哪一步，以及继续该步骤所需的条件。已有的禁止、停止、HOLD 或失败结论保持明确。可独立推进的工作按现有授权继续，恢复条件由对应流程确定。

交付前，从读者角度核对：是否清楚当前可以说什么、下一步先做什么，以及哪些必要条件会改变动作或结论。

### 任务代号与编号

需要在多份记录中反复引用同一任务、批次、方案或证据集合时，才设置代号；一次性对象直接写名称。代号首次出现必须写全称，并在括号中给出代号，例如“Windows 脚本静态检查（M1）”。从代号和首次说明中，读者应能判断对象、范围和阶段。代号只用于索引，不替代状态、结论、授权或文件路径。

每个分类单独定义前缀和序列；同一序列固定一种含义和一种递增规则（时间或版本二选一），不得跨分类或跨序列复用同一代号。相近序列使用不同前缀或关键词，并写明关系。计划、TODO、交接和证据引用沿用同一代号定义。对象或范围变化时建立新代号，说明与旧代号的关系，并保留旧记录和已有引用。能用名称或日期清楚表达时，不强行增加代号。

### 中文说明写法

本节只约束面向用户的中文进度、交接和审查说明；shell 命令、JSON/schema/manifest、英文机器标识和安全控制语义按原规则执行。

写进度、交接或审查结论时，先说明当前状态；如果状态是 HOLD、FAIL、NOT_RUN、UNVERIFIED，或当前存在安全限制，第一句先写状态和原因。随后列出已完成的动作、证据路径或 SHA-256，以及证据覆盖的范围；最后写尚缺的证据、下一步和所需授权。每句只表达一个动作或结论。术语第一次出现时，用常用话解释。

普通说明优先使用具体的动词、条件和结果。少用“冻结、契约、门禁、边界”等抽象词，也少用“不是……而是……”的对照句。正式治理条款、安全规则、状态值、代码/API/schema 名称、检查项名称和证据范围名称保留原样。需要说明限制时，用证据范围来写：

- 当前证据只支持静态检查；运行时效果仍需通过<具体独立验证>确认。
- 当前验证覆盖<真实范围>；效果仍需通过<具体验证>确认。
- 额度配置保持当前值；质量是否恢复要通过已获授权的换出口独立测试确认。

交付前检查以下内容：

1. 涉及事实或状态的段落先写当前状态或完成动作，并附证据路径或 SHA-256；规范性段落写适用条件和可执行动作。
2. 说明当前状态、尚缺证据、下一步和前置授权；示例中的 <...> 占位符必须替换成当前记录中的真实范围和动作。
3. 检查机器可读状态、路径、哈希和数值没有被同义改写。
4. 对“百分百、保证、恢复”等断言逐一核对证据；删掉不必要的“不是……而是……”句式；安全限制后面写出真实的允许条件、待授权动作、恢复条件或验证证据。

“不得执行”“禁止”、HOLD/FAIL/NOT_RUN/UNVERIFIED 和 fail-closed 条件不能被弱化。说明原因后，紧接着写允许条件、待授权动作、恢复条件或验证证据；这些内容必须来自当前授权或控制记录，不得自行推断。

## 阶段路由模型

阶段是按任务选择的能力模块，不是每个请求都必须串行走完的流水线。先识别任务类型、风险和外部副作用，再选择最短且证据充分的可选路径：

| 任务类型 | 默认路径 | 关键准出证据 |
|---------|---------|-------------|
| 已知目标的轻量文档/配置变更 | 目标确认 → 修改 → 静态校验 → diff 审查 | 结构有效、引用可解析、无意外改动 |
| 功能开发 | 需求/取舍 → 风险匹配的计划 → 实现 → 回归验证 | 行为测试、相关质量闸门、已知偏差 |
| Bug 修复 | 复现/证据 → 根因 → 修复 → 回归验证 | 失败用例转绿、相邻路径无回归 |
| 代码审查 | 范围确认 → 证据审查 → 风险排序 → 结论 | 可定位发现、测试缺口、残余风险 |
| 性能优化 | 基线 → 瓶颈证据 → 单变量变更 → 等价性与基准复测 | 可复现实测、输出契约不变 |
| 安全/数据/生产变更 | 诊断/威胁建模 → 正式计划 → 授权点 → 实施 → 扩展验证 → 收尾 | 回退可用、审计证据、明确残余风险 |

**门控规则**：
- 只检查当前路径适用的前置条件；不适用阶段标记 `N/A` 并简述原因，无需为了形式补齐。
- 原因未知、症状可能来自多层系统或修复依赖根因时先诊断；目标与改法均明确的窄小变更可直接规划或实施。
- 高风险方案未经必要评审，或关键决策、授权点和回退策略未明确时，不进入实施。
- 行为变更必须取得与风险匹配的失败证据或基线，再通过回归；文档与配置变更使用结构、引用和静态校验。
- 验证发现偏差时回到相关阶段修复；无法消除的偏差必须显式记录，不能以放宽阈值掩盖。
- 同一闸门反复失败且没有新证据时暂停，重新检查假设与方案；不使用固定重试次数代替判断。
- 收尾、文档同步和知识持久化仅在用户要求、仓库惯例或后续维护确有价值时执行。

## 何时使用

所有改动都保留同一骨架：理解目标 → 控制风险 → 取得证据 → 清理现场。执行深度按风险和影响面调整：

| 级别 | 典型条件 | 最低流程 |
|------|----------|----------|
| 轻量 | 局部、可逆、不改变运行行为 | 简短目标 + 针对性静态检查 + diff 审查 |
| 标准 | 行为变更、Bug 修复、多个关联文件 | 可追踪计划 + 回归测试 + 相关质量闸门 + 三 C |
| 高风险 | 安全/数据/生产、跨模块、不可逆或外部副作用 | 正式操作指引 + 回退/备份 + 扩展测试与审查 + 明确授权点 |

文件数只用于估算影响面，不单独决定风险。紧急变更可以压缩说明，但不能省略可回退性和正确性证据。

## 可选能力衔接

先使用本插件内与当前任务匹配的子 Skill。需要额外能力时，先从当前运行时已声明的 Skill、MCP、Agent 和仓库工具中发现可用项；没有专用能力时继续使用项目原生工具链，不因某个外部名称不存在而阻塞。

| 触发条件 | 所需能力 | 选择原则 |
|---------|---------|---------|
| 需求或取舍仍不清楚 | 方案探索与决策梳理 | 优先使用已发现的发散/决策能力；否则在计划中列出选项、证据和取舍 |
| 常规调试仍未定位 | 深层根因追踪 | 选择能观察调用链、状态或运行时证据的可用能力 |
| 非平凡实现需要独立审查 | 代码审查 | 使用可用审查能力或由独立审查者检查正确性、回归和测试缺口 |
| 需要确认实际运行效果 | 运行时或端到端验证 | 使用项目原生启动、冒烟或 E2E 工具；只执行当前环境允许的动作 |
| 涉及安全敏感改动 | 安全审查 | 使用已发现的安全检查能力，并按威胁面补充人工审查 |
| 配置或权限需要调整 | 配置校验与授权 | 使用仓库已有 schema/解析器；外部状态变更前取得必要授权 |

## 迭代机制

本 skill 需要在项目实践中持续优化。当以下情况出现时（无论哪个项目），会通过对应项目的特化版触发更新流程：

1. **发现新的有效工作方法** — 某类问题的排查顺序、验证策略被验证有效
2. **识别出新的反模式** — 反复出现的错误模式值得纳入文档
3. **发现准则空白** — 已有文档没有覆盖到的场景或环节

更新流程：
1. 先写入对应项目的特化版（含项目特化表述）
2. 再去除特化表述，同步到本通用版
3. 对总纲、铁律与核心流程内容本身的更新/替换属于重要文件变更——先按铁律 B6 完成留痕与审批；旧版本说明、历史版本记录与归档不得删除。

每个独立 PR 在合并进入 `master` 前，都要为受影响插件选定一次版本并写变更说明；版本更新属于这次变更的一部分，版本更新本身不会再次触发递增。文档、测试和小修正至少递增 PATCH；功能新增递增 MINOR；不兼容变更递增 MAJOR；同一 PR 含多种类型时取最高级别（MAJOR > MINOR > PATCH），多个插件分别判定。只更新一个插件时，其他插件沿用原版本。插件发布元数据和发布记录中的版本号（`package.json`、插件 `plugin.json`、marketplace、README、测试断言及本次变更记录）必须保持一致；总纲的 3.x 方法论版本独立维护，旧版本记录保留。
