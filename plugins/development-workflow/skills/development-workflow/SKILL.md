## 概述

在系统优化与功能开发中，每一次代码改动都是对既有系统的扰动。本 skill 的目标是在「快速迭代」和「系统稳定性」之间建立硬约束——用可量化的验证替代直觉判断，用结构化的流程降低回溯成本。

**核心信念**：
- 「看起来对了」不足以支持完成声明 —— **验证需要明确判据与可核验依据；能量化时量化**。
- 「先动手再说」是返工的起点 —— **先明确目标、风险和验收证据，再选择与影响面匹配的流程**。
- 「肯定是环境/方案/库的问题」是排查的天敌 —— **从最接近改动且最容易证伪的假设开始，不用未经验证的概率替代证据**。

本方法论提炼自真实项目的完整开发-调试-验证-维护循环，面向 AI 编码助手协作场景，泛化至任何语言/框架/项目类型。

## 铁律体系

铁律分为两类：**工具使用铁律**（编辑纪律与安全）和 **流程铁律**（过程纪律）。

### 一、工具使用铁律

```
铁律 A1：手工修改必须使用当前运行时提供的可审计结构化编辑机制。
         —— Claude Code 使用 Edit/Write，Codex 使用 apply_patch；格式化器、代码生成器
         等确定性批量工具可按项目惯例执行。创建、移动和删除前确认目标路径与作用域，
         不用跨 shell 拼接路径执行破坏性操作。

铁律 A2：保护敏感隐私信息，不得以任何形式泄露。
         —— MCP 调用前检查参数是否含凭据；不打印完整 Key；
         不上传项目数据到未授权第三方。

铁律 A3：在用户授权的范围内执行 Git 和外部操作。
         —— 已有授权持续适用于明确的仓库、目标分支和操作范围；以用户最新指令为准。
         接手保留授权来源及用户设定的次数、时限或撤销条件；已消耗的一次性授权、
         已到期或已撤销的许可不能续用。普通持续授权无需反复索取，交接或计划本身不产生授权。
         提交前核对 diff 和相关检查，选择本任务文件。新增发布目标、破坏性操作或
         超出授权范围时，先完成可独立推进的准备，再向用户说明需要决定的具体事项。

铁律 A4：按任务需要发现并选择工具，不假定某个 plugin、MCP、skill 或 agent 存在。
         —— 工具的价值是减少不确定性或提供更可靠的执行能力；调用数量本身不是目标。

         执行细则：
         a) 先看已声明能力，再按当前步骤选择最小充分工具集；不得凭记忆猜测可用性。
         b) 专用工具能显著提高正确性、速度或可追溯性时调用；否则使用仓库已有工具链。
         c) CodeGraph 仅在仓库存在 `.codegraph/` 时优先使用；不存在时直接回退到 `rg`
            和文件读取，不自行创建索引。
         d) 多工具重叠时的决策：
            · 常规任务：选择最适配的一个
            · 仍有具体疑点：增加能回答该疑点的工具或专项审查
            · 不确定时：先做低成本只读检查，再决定是否扩大工具集合
```

### 二、流程铁律

```
铁律 B1：计划先行，执行在后。
         —— 开始实现前至少明确目标、影响面、步骤和验收证据。跨模块、高风险、
         不可逆或存在关键取舍的变更写成操作指引；窄小且可逆的变更可用简短计划。
         只有缺失的决策会改变范围、风险或外部状态时，才需要暂停等待用户确认。

铁律 B2：TODO 与计划严格对照。
         —— 有显式计划时，TODO、实施和验证证据必须能对应；执行中发现范围变化，
         先更新计划。简单任务无需为了形式重复维护两份等价清单。

铁律 B3：在有意义的阶段检查进展，发现偏差及时处理。
         —— 对照当前目标与验收标准；一般偏差直接修复并检查受影响部分。
         只有范围、方案或用户决策发生变化时更新计划，避免每步重复重读全部材料。

铁律 B4：所有代码变更必须过测试闸门。
         —— 先根据变更类型、风险和仓库能力选择适用闸门：行为变更走失败测试→实现→
         回归；文档/配置走结构或静态校验；安全敏感和跨模块变更扩大审查范围。
         所有适用闸门通过后才进入下一阶段；无法运行的闸门必须说明原因与残余风险。

铁律 B5：保护数据完整性。
         —— 数据处理变更必须区分缺失、不适用与合法零值，并定义与领域契约一致的
         不变量和失败条件。只有在"关键字段不应全零"确为业务不变量时才硬阻断。

铁律 B6：让重要修改可理解、可恢复，并按实际影响选择审查。
         —— Git 历史与 diff 用于记录源码修改；提交历史或已有备份无法恢复的独有内容，
         包括已跟踪文件中未提交的原有改动，在覆盖或删除前备份一次。沿用已有授权，检查与当前改动有关的问题。
         细则见《重要修改的记录与恢复》。
```

## 重要修改的记录与恢复

### 记录与备份

- 记录改了什么、原因和验证结果；使用现有 PR、提交或对应文档作为一个主要记录位置。
- 已提交内容通过 Git 历史恢复。提交历史或已有副本无法恢复的内容（包括已跟踪文件中未提交的原有改动），在替换前保存一次可读副本或补丁。
- 普通编辑使用正常读回、diff 和相关测试；SHA-256 用于需要确认内容完整性的归档传输、发布包或恢复操作。
- 历史失败和关键决策保留。重复副本确认已有可恢复来源后，可以按用户要求整理。
- 普通工作区路径边界、八类目录分类、轻量 `.tmp/` 与 OS 临时区租约（`TempLease1`）、六门控无损脱水（`DehydratedBundle1`）及不可变冷归档（`ArchiveManifest1`）统一由 [dw-file-governance](../dw-file-governance/SKILL.md) 规范；多智能体受管后台进程与子租约配额协议仍由 [dw-collaboration](../dw-collaboration/SKILL.md) 维护。

### 审查与授权

- 常规可逆修改：直接实施，完成相关检查与 diff 复核。
- 非平凡代码修改：进行一次适当范围的审查，修复发现后复核受影响部分。
- 涉及权限、数据损失、生产影响或恢复操作：补充能回答具体风险的检查；必要时安排独立专项审查。
- 已有授权覆盖的事项继续执行。确实缺少用户决定时，说明具体选择、影响和建议。
- 文件的重要程度用于确定检查内容；多人一致同意、固定审查轮数、逐次哈希和新开审核对话均不作为通用要求。
- 身份、权限、owner 或回滚验证属于具体运行功能时，继续遵守该功能的要求；记录缺失导致的 HOLD 及恢复条件。

## 对外表达与建议方式

所有工作以用户目标及其可观察的完成条件为准。功能交付、研究结论、文档整理和监控建设各有自己的验收对象；支持性材料完成不等于被支持的功能或研究已验证，也不因它是文档工作就否认其已完成的交付。

各子 Skill 的用户说明遵循 [dw-writing](../dw-writing/SKILL.md)：先写结果与具体动作，按证据说明范围和下一步。中文用词、限制说明及任务名称/代号在该 Skill 集中维护，也可单独调用。

事实、授权、安全要求和机器可读状态由对应流程确定，文字调整须准确保留其语义。

### 中英双语分工原则（Domain-Aligned Bilingual Policy）

为让不同模型在各自擅长领域发挥最高精度，本插件采用**按领域分工的中英双语策略**，不强制单语化：

- **形式化契约与系统原语保持英文主叙事**：多智能体状态机、OS 进程/Job/进程组监管、JSON Schema 契约（如 `TempLease1`、`DehydratedBundle1`、`ArchiveManifest1`、`DwTodoPlan1`）、CLI 参数与机器状态标识（`HOLD`、`UNVERIFIED`、`PASS_STATIC`、`PASS_FOCUSED`、`NOT_RUN`、`FAIL`、`TaskResourceManager`）及常驻规则 [rules/development-workflow.md](../../rules/development-workflow.md) 以**英文**作为权威锚点，并在入口处附中文导航说明，避免翻译漂移削弱形式化推理精度。
- **研发流转、沟通与文档表达采用中文加英文标准术语**：阶段路由、诊断定位、规划取舍、人机协作（`dw-interaction`）、技术写作（`dw-writing`）与交接（`dw-handoff`）以**中文**为主体，同时在标题与触发描述中嵌入规范英文术语锚点（如 `Root-Cause Diagnosis`、`Minimal Reproducer`、`RED-GREEN-REFACTOR`、`3C: Consistency / Completeness / Correctness`、`Fail-Closed`）。
- **面向用户的最终答复**：始终跟随用户当前提问所使用的语言（遵循 `dw-writing`）。

## 授权、资源与内部前置条件

这是各子 Skill 共用的执行原则；角色分工、进度模板、平台适配器或任务板不另外产生审批要求。

- **已有授权**：明确目标和操作范围已获授权时，继续完成相应工作。换角色、写计划、进入下一阶段或普通重试本身不要求重新批准；用户明确要求“先给方案、等批准”时，保留这个边界。
- **资源调度**：并发额度、端口或计算资源占用时，先排队、串行或推进独立部分；仅当需要用户取舍优先级、追加预算或扩大资源范围时提问。缺少真实依据时不承诺可用时间。
- **内部前置条件**：自行增加的清单、命名、审批记录或任务板字段由执行者补齐、简化或撤去。报告真实阻塞时给出来源、受影响步骤、已尝试的替代路径和用户需要决定的最小事项。
- **失败与消耗**：区分工程故障、资源等待、验收不通过和用户取消。工程故障不自动证明方案失败；查明可改变结果的原因后，可在剩余授权和预算内重试。已经消耗的费用、算力、时间和次数照实累计，新 attempt 不重置限额。无新依据、预算耗尽或明确停止时停止相应尝试，保留其他可推进工作。
- **证据范围**：默认使用可访问的文件、提交/diff、运行标识、命令和结果。需要定位时附行号，需要确认传输、发布、恢复字节或具体协议要求时使用哈希；不要求每条消息和普通交接都附大小及哈希。同一输入、实现和环境下仍适用的检查可复用，并注明覆盖范围与未重跑部分。

## 脚本约束与人工判断

脚本适合检查确定且可观察的条件：输入结构、依赖是否满足、写入归属、额度扣减、状态转换、退出结果和发布文件是否齐全。检查应位于真实副作用发生前及结果收尾处；先失败后仍继续启动，或只有一份未被调用的校验库，都不能算执行约束已接入。

采用脚本前明确保护的对象、调用入口、失败时的行为和反例测试，复用已有检查器及宿主能力。错误的需求、方案取舍、证据能否支持结论、用户授权的含义仍需语义判断，不按关键词、消息次数或哈希数量机械决定。不为普通讨论配置完整资源管理器。

报告实现状态时分别说明：规则是否写明、实现是否存在、真实入口是否调用、测试使用真实对象还是替身、目标宿主是否验证。缺少生产适配器、进程身份或终态证据时保留未完成/未知，不能凭测试通过推定已经接管全部任务或进程。DW 的对应入口及限制见[自动化覆盖清单](../dw-tooling/references/automation-coverage.md)；该清单的静态校验只证明登记与引用完整。

方案追问与外部方法取舍见[方法整合说明](../dw-reference/references/method-integration.md)。按当前问题选择有用步骤，沿用已有授权，不恢复固定阶段审批或固定审查人数。

## 阶段路由模型

阶段是按任务选择的能力模块，不是每个请求都必须串行走完的流水线。先识别任务类型、风险和外部副作用，再选择最短且证据充分的可选路径：

| 任务类型 | 默认路径 | 关键准出证据 |
|---------|---------|-------------|
| 已知目标的轻量文档/配置变更 | 目标确认 → 修改 → 静态校验 → diff 审查 | 结构有效、引用可解析、无意外改动 |
| 功能开发 | 需求/取舍 → 风险匹配的计划 → 实现 → 回归验证 | 行为测试、相关质量闸门、已知偏差 |
| Bug 修复 | 复现/证据 → 根因 → 修复 → 回归验证 | 失败用例转绿、相邻路径无回归 |
| 代码审查 | 范围确认 → 证据审查 → 风险排序 → 结论 | 可定位发现、测试缺口、残余风险 |
| 性能优化 | 基线 → 瓶颈证据 → 单变量变更 → 等价性与基准复测 | 可复现实测、输出契约不变 |
| 涉及安全、敏感数据、数据损失或生产影响的变更 | 诊断/威胁建模 → 正式计划 → 授权点 → 实施 → 扩展验证 → 收尾 | 回退可用、审计证据、明确残余风险 |

**门控规则**：
- 只检查当前路径适用的前置条件；不适用阶段标记 `N/A` 并简述原因，无需为了形式补齐。
- 原因未知、症状可能来自多层系统或修复依赖根因时先诊断；目标与改法均明确的窄小变更可直接规划或实施。
- 高风险方案未经必要评审，或关键决策、授权点和回退策略未明确时，不进入实施。
- 行为变更必须取得与风险匹配的失败证据或基线，再通过回归；文档与配置变更使用结构、引用和静态校验。
- 验证发现偏差时回到相关阶段修复；无法消除的偏差必须显式记录，不能以放宽阈值掩盖。
- 同一闸门反复失败且没有新证据时暂停，重新检查假设与方案；不使用固定重试次数代替判断。
- 收尾、文档同步和知识持久化仅在用户要求、仓库惯例或后续维护确有价值时执行。

## 何时使用

所有改动都保留同一骨架：理解目标 → 控制风险 → 取得证据 → 清理现场。执行深度按风险和影响面调整：

| 级别 | 典型条件 | 最低流程 |
|------|----------|----------|
| 轻量 | 局部、可逆、不改变运行行为 | 简短目标 + 针对性静态检查 + diff 审查 |
| 标准 | 行为变更、Bug 修复、多个关联文件 | 可追踪计划 + 回归测试 + 相关质量闸门 + 三 C |
| 高风险 | 安全、敏感数据、数据损失、生产影响、关键跨模块契约、不可逆或重要外部副作用 | 正式操作指引 + 回退/备份 + 扩展测试与审查 + 明确授权点 |

文件数只用于估算影响面，不单独决定风险。紧急变更可以压缩说明，但不能省略可回退性和正确性证据。

## 可选能力衔接

先使用本插件内与当前任务匹配的子 Skill。需要额外能力时，先从当前运行时已声明的 Skill、MCP、Agent 和仓库工具中发现可用项；没有专用能力时继续使用项目原生工具链，不因某个外部名称不存在而阻塞。

| 触发条件 | 所需能力 | 选择原则 |
|---------|---------|---------|
| 需求或取舍仍不清楚 | 方案探索与决策梳理 | 优先使用已发现的发散/决策能力；否则在计划中列出选项、证据和取舍 |
| 常规调试仍未定位 | 深层根因追踪 | 选择能观察调用链、状态或运行时证据的可用能力 |
| 非平凡实现需要独立审查 | 代码审查 | 使用可用审查能力或由独立审查者检查正确性、回归和测试缺口 |
| 需要确认实际运行效果 | 运行时或端到端验证 | 使用项目原生启动、冒烟或 E2E 工具；只执行当前环境允许的动作 |
| 涉及安全敏感改动 | 安全审查 | 使用已发现的安全检查能力，并按威胁面补充人工审查 |
| 配置或权限需要调整 | 配置校验与授权 | 使用仓库已有 schema/解析器；外部状态变更前取得必要授权 |

## 迭代机制

本 skill 需要在项目实践中持续优化。当以下情况出现时（无论哪个项目），会通过对应项目的特化版触发更新流程：

1. **发现新的有效工作方法** — 某类问题的排查顺序、验证策略被验证有效
2. **识别出新的反模式** — 反复出现的错误模式值得纳入文档
3. **发现准则空白** — 已有文档没有覆盖到的场景或环节

更新流程：
1. 已有项目特化文档时，在相关位置记录有复用价值的本地结论
2. 确有通用规则需要修订时，去除项目特化假设，在已授权范围内更新本通用版
3. 总纲与核心流程的修改按铁律 B6 保留可恢复版本，完成与影响相符的检查，并更新当前说明。

版本递增、发布目标和元数据同步遵循目标仓库的维护与发布策略。同一次变更中的版本元数据修订不应再次触发递增；总纲的方法论版本独立维护，历史记录保留。提交准备见 [dw-wrapup](../dw-wrapup/SKILL.md#提交准备)。
