# 优化方法论（Performance & Resource Optimization）

> 本 skill 是 [development-workflow](../development-workflow/SKILL.md) **L2 专项技术深潜** 子模块，覆盖 **性能与资源优化核心方法**（量化基线、决策树与功能等价验证）。

---

## 优化核心原则

任何优化必须遵循以下五条原则：

1. **功能等价（Functional Equivalence）**：优化不得改变原有行为。相同输入必须满足该 API 预先定义的精确或数值容差契约；浮点或非确定性路径不得事后放宽容差。
2. **可替换性（Drop-in Replacement）**：优化后的代码应能无缝替换原代码，接口不变。
3. **可验证性（Verifiability）**：每次优化必须附带验证手段——功能测试确认行为不变，性能测试确认加速真实。
4. **渐进优化（Incremental）**：优先优化热点路径。不做无目标的提前优化。
5. **可读性折中（Readability Trade-off）**：优化不应过度损害可读性。显著牺牲可读性的优化需附加注释说明意图。

## 优化决策树（Optimization Decision Tree）

在决定是否优化以及如何优化前，按以下顺序逐级评估：

```
1. 是否有性能问题？               → 无 → 不优化（保持现状）
   ↓ 是
2. 是否是对目标指标有实质贡献的热点？ → 否 → 标记暂缓，不投入时间
   ↓ 是
3. 是否有更优的算法？             → 是 → 算法优化（复杂度降级/预计算/早期退出）
   ↓ 否
4. 是否有更优的库可替代？         → 是 → 库替换优化（向量化/更快的数据格式）
   ↓ 否
5. 是否适合 JIT 编译？           → 是 → JIT 优化（先计入预热与部署成本）
   ↓ 否
6. 是否有不必要的 IO？           → 是 → IO 优化（批量读写/延迟加载/条件跳过）
   ↓ 否
7. 是否可以并发/并行？           → 是 → 按 GIL、IPC、配额和依赖线程池实测选择模型
   ↓ 否
8. 是否可以 GPU 加速？          → 是 → GPU 优化（合并内核启动/减少传输）
   ↓ 否
9. 保持现状，标记未来关注
```

**原则**：无基线与 profiling 不优化。热点阈值来自用户目标、调用频率和端到端影响，不使用全局固定百分比。

## 六类优化层级概览（Optimization Tiers）

具体语言示例、代码模板（Python/NumPy/Numba/CUDA）与逐项检查清单按需读取 [六类优化代码示例与检查清单](references/optimization-patterns-and-examples.md)：

| 层级 | 核心手段 | 关键前提与约束 |
|------|----------|---------------|
| 1. 算法优化 | 复杂度降级、预计算 LUT、早期退出 | 优先带来数量级收益，不依赖硬件 |
| 2. 库与向量化 | 原生高性能库、向量化/批量替代逐元素循环 | 确认语义等价，避免不必要拷贝 |
| 3. JIT 编译 | 热点数值循环静态化并开启编译缓存 | 同输入同环境对比冷启动、稳态与端到端耗时 |
| 4. IO 优化 | 批量读写、按需加载、重复内容缓存 | 保持追加、崩溃恢复与内存契约；不可信输入禁 pickle |
| 5. 并发并行 | IO 密集用协程/线程；CPU 密集实测多进程或释放 GIL 库 | 实测 GIL/IPC 成本；异常路径关闭 executor 并回收子进程 |
| 6. GPU 优化 | 合并计算内核启动、控制 batch 与减少 host↔device 拷贝 | 确认批量处理与原调用语义等价；防显存 OOM |

## 性能分析流程

1. **宏观定位**：优先使用仓库/语言原生 profiler 定位端到端热点
2. **微观分析**：对候选热点量化子步骤，同时保留真实调用上下文
3. **资源分析**：按目标检查内存、I/O、CPU、GPU、网络或外部服务等待
4. **根因确认**：确认瓶颈在算法/IO/计算/显存传输的哪一环

**Benchmark 方法论**：

- 用本地代表性工作负载覆盖常见规模和已知边界，不按固定帧数套模板。
- 先定义时间预算或误差目标，再自适应增加重复次数；报告样本数、中位数、尾延迟和离散度。
- 分开测冷启动与稳态；JIT 记录预热，GPU 在计时边界同步，缓存场景区分冷/热。
- 比较候选库时锁定版本、输入、配置和硬件，并先验证输出语义等价。

**对比基线要求**：
- 优化前后的代码在**同一硬件环境**上运行
- 记录并尽量控制系统负载；样本不足或方差过大时不得宣称提升
- 记录测试环境（CPU/GPU/内存/运行时与关键库版本）

## 库与实现选型协议

静态性能排行榜会随版本、硬件、数据分布和配置失效。比较 DataFrame、可视化、模型、图像 I/O、序列化或进度展示方案时：

1. 先列硬约束：正确性、格式/接口兼容、内存上限、部署体积、维护状态和安全边界。
2. 用仓库真实版本构造最小但代表性的本地基准；测量端到端路径，不只测微内核。
3. 同时记录迁移成本、可读性、可观测性和回退方案；最快不自动等于最佳。
4. 选定方案后把环境、输入、命令、统计量和功能等价结果写入变更证据。

## 优化反模式

| 反模式 | 影响 | 处理方式 |
|--------|------|----------|
| 无基线或 profiling 就选优化目标 | 不能证明该路径影响目标指标 | 用代表性负载确认瓶颈与端到端贡献 |
| 过早优化非热点 | 增加实现成本，核心目标仍未达成 | 先满足正确性，再按瓶颈证据投入 |
| 省略适用的功能等价检查 | 局部加速可能改变输出或集成行为 | 按受影响边界选择单元、集成和回归证据 |
| 收窄输入范围或改变接口/返回类型 | 优化不能直接替换原实现 | 保留原契约；确需改变时按独立行为变更规划 |
| 以少量收益引入大量复杂代码 | 维护与迁移成本超过可复现收益 | 同时评估实测收益、可读性与恢复成本 |
| 删除必要说明或保留过时注释 | 后续维护者误解前提与算法 | 保留设计理由，更新与实现不一致的注释 |
| 只测单一规模 | 固定开销、扩展性和边界退化未覆盖 | 选择代表实际风险的规模、边界与冷/热条件 |
