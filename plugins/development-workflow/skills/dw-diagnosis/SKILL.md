# 诊断与根因定位

> 本 skill 是 [development-workflow](../development-workflow/SKILL.md) 的子模块，覆盖 **阶段一：诊断与根因定位**。

**核心原则：永久修复前先取得足以区分根因的证据。** 生产事故可先做可逆隔离、回滚或关闭开关来降低影响，但必须把临时 containment 与永久修复分开记录，并继续根因分析。

---

## 诊断流程

### 第 1 步：收集多维度证据

先稳定复现并写出候选假设，再选择成本最低、最能区分假设的证据。无需机械收集所有类别；当证据能稳定复现、排除关键替代解释并支持下一步决策时停止。

| 角度 | 方法 | 工具 |
|------|------|------|
| 数据输出 | 检查异常值、分布和边界 | 结构化解析器或项目分析工具 |
| 可视化产物 | 查看生成的图片/视频，检查视觉异常 | 当前运行时可用的媒体查看能力 |
| 日志 | 搜索错误、警告和异常栈 | `rg` 或结构化日志查询 |
| 配置 | 对比运行组与默认值 | 仓库 diff/配置解析工具 |
| 数据流 | 从输出反查输入，追踪上游来源 | 有 `.codegraph/` 时用 CodeGraph；否则用 `rg` 和文件读取 |
| API 文档 | 查证第三方库/API 约定 | 当前版本的官方文档或可用文档工具 |

### 第 2 步：建立假设并交叉验证

- 对每个候选根因写出明确假设："我认为 X 是根因，因为 Y 证据"
- 用多个独立来源的证据交叉验证同一假设
- 区分"相关"与"因果"——多个根因可能叠加

### 第 3 步：分开记录影响、原因与置信度

不要把严重度和原因类型混在同一轴：

| 维度 | 取值示例 | 用途 |
|------|----------|------|
| **影响** | 阻塞 / 高 / 中 / 低 | 决定响应优先级 |
| **原因层** | 代码 / 配置 / 数据 / 依赖 / 环境 / 需求 | 决定修复责任与位置 |
| **置信度** | 已复现 / 高 / 中 / 低 | 表明证据强度，避免把猜测写成结论 |
| **可修复性** | 可直接修 / 需迁移 / 需外部协作 / 仅可缓解 | 决定下一步行动 |

### 第 4 步：评估修复优先级

按影响与紧迫性、依赖顺序、可逆性和修复成本排序。上游问题通常影响更广，但生产隔离、展示误导或安全风险可能需要优先处理；不要用固定层级替代当前证据。

---

## 诊断反模式

- ❌ 看到"全零"就加 `if zero: fix()`——先找出为什么是零
- ❌ 一个症状对应一个 fix——多个症状可能共享同一根因
- ❌ 只检查代码不检查数据——输出文件是最客观的证据
- ❌ 修复第一个找到的 bug 就停——叠加 bug 是常态

---

## 诊断检查清单

```
□ 症状可稳定复现，或已明确说明无法复现的限制
□ 每个候选根因有明确假设和证据
□ 关键替代假设已被区分，不再机械追加低价值证据
□ 影响、原因层、置信度和可修复性已分别记录
□ 修复优先级已确定
□ 临时 containment 与永久修复已分开记录
```
