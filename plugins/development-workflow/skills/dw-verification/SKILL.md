# 系统性验证与偏差修复

> 本 skill 是 [development-workflow](../development-workflow/SKILL.md) 的子模块，覆盖 **系统性验证与偏差修复**。遵循铁律 B3（偏差分级修复）。

**核心原则：完成声明必须由与风险匹配、可复现且新鲜的证据支持；能量化时量化，不能量化时给出明确判据。**

---

## 验证循环（计划→实现逐项对照）

实施完成后，执行完整的计划→实现对照验证：

```
FOR EACH 计划子步骤:
    1. 定位计划中的具体描述
    2. 定位对应实现（有 `.codegraph/` 时可用 CodeGraph，否则用 `rg`/文件读取）
    3. 验证: 功能是否完全对应？逻辑是否一致？
    4. 标注: 完全匹配 / 部分匹配（注明差异） / 缺失
    5. 汇总偏差清单，按严重度分级（见 §偏差严重度分级）

FOR EACH 偏差:
    1. 重读计划中的对应段落，确认差异不是理解偏差
    2. 记录证据、严重度、影响和建议行动
    3. 若任务仅要求验证/审查：报告偏差，不修改文件
    4. 若用户已要求修复：实施最小修复，再对照并运行相关测试
```

## 三 C 判定标准

### 验证金字塔（三层，从底到顶）

```
        ┌──────────┐
        │  集成验证  │  ← 端到端运行，确认整体指标未退化
       ┌┴──────────┴┐
      ┌┴────────────┴┐
      │  功能验证     │  ← 断言 / 中间态输出，确认逻辑分支正确
     ┌┴──────────────┴┐
     │  编译/语法验证   │  ← import 通过、无语法错误
     └────────────────┘
```

- **编译/语法验证**：使用仓库已有的构建、解析、类型或结构校验；纯文档变更不强行运行无关编译。
- **功能验证**：断言测试、新旧结果对比、中间态打印校验
- **集成验证**：运行完整 pipeline，确认产出指标在预期范围内

### 三 C 判定

| C | 名称 | 检查项 | 验证方法 |
|---|------|--------|---------|
| 1 | **Consistency（一致性）** | 实现与操作指引一致？无「惊喜」逻辑？参数/配置与设计一致？ | 逐条对照 TODO list |
| 2 | **Completeness（完整性）** | TODO 全部实现？边界/异常/错误处理齐全？配套产出齐全？回退/关闭机制存在？ | Checklist 逐项打勾 |
| 3 | **Correctness（正确性）** | 编译/导入通过？功能/集成验证通过？量化指标在预期范围？ | 量化对比 + 基线对比 |

**三项必须同时通过，缺一不可。**

### 三 C 循环

```
        开始验证
            │
            ▼
      ┌──────────────┐
      │  一致性检查    │ ← 不通过 → 回到实现修正偏离
      └──────┬───────┘
             ▼ 通过
      ┌──────────────┐
      │  完整性检查    │ ← 不通过 → 补充遗漏实现
      └──────┬───────┘
             ▼ 通过
      ┌──────────────┐
      │  正确性检查    │ ← 不通过 → 修复（先查实现错误）
      └──────┬───────┘
             ▼ 全部通过
          验证通过 ✅
```

- 单次未通过 → 回到对应实现修改
- 指引本身有问题（逻辑矛盾/物理不可行）→ 回到方案设计修订指引
- 同一验证反复失败且没有新增证据 → 暂停盲目重试，重新评估根因或方案

## 偏差严重度分级

| 级别 | 定义 | 行动 |
|------|------|------|
| **P0** | 阻塞性偏差——核心功能缺失或错误 | 立即修复，暂停其他工作 |
| **P1** | 重要偏差——影响验证完整性或数据质量 | 当前阶段修复 |
| **P2** | 次要偏差——文档、注释、测试覆盖不足 | 下阶段修复或记录为技术债 |
| **P3** | 低影响偏差——不影响当前行为与验收 | 记录或按范围处理 |

外部依赖缺失不是严重度：用 `BLOCKED` 或 `UNVERIFIED` 单独标记，并列出缺失的硬件、网络、凭据或人工动作。

## 功能等价验证层次（性能优化改动专属）

性能优化在三 C 之外还需验证**功能等价**——优化前后输入相同则输出必须相同：

| 级别 | 测试内容 | 方法 | 接受标准 |
|------|---------|------|---------|
| L1 | 单元等价 | 对优化函数用相同输入调用新旧版本 | 满足该 API 的精确或数值容差契约 |
| L2 | 集成等价 | 在完整管线上对比优化前后的输出产物 | 结构、语义与允许差异符合契约 |
| L3 | 回归等价 | 运行项目评估流程对比报告 | 核心指标不超过预先定义的退化预算 |

**浮点差异处理**：容差来自数值尺度、算法稳定性和业务误差预算，并在看结果前定义；不得套用全局固定值或为通过测试事后放宽。

## 实测驱动调试

当单元测试通过但集成/硬件测试失败时，进入**实测驱动调试**模式：

1. **最小独立复现**：隔离与故障相关的最少依赖，必要时绕过项目框架直接调用底层 API；规模以能稳定复现且便于审查为准
2. **对照实验设计**：每次只改变一个变量，其他条件完全相同
3. **观察→假设→验证循环**：每一轮实验产出一个明确结论
4. **证据链完整**：从实验结论→代码修改→测试通过，每一步都可追溯

---

## 测试阈值校准

- 合成数据的 ground truth 与算法输出之间存在固有误差（算法不可能完美恢复精确变换）
- 阈值由基线噪声、数值尺度和业务误差预算共同确定，并在查看候选结果前记录理由
- 失败后不得只为过测放宽阈值；先判断实现、数据、环境或原阈值模型哪一项有新证据
- 合法全零、空输入或不适用状态按领域契约处理，不把“非零”当作通用正确性标准

## 选择验证命令

1. 先读取仓库说明、package scripts、任务运行器和 CI 配置，找出项目原生命令。
2. 从受影响行为反推最小测试集，再按风险扩展到构建、集成、端到端或安全检查。
3. 文档、配置和 Skill 变更优先运行链接、schema、结构或解析校验，不套用无关语言命令。
4. 记录实际命令、退出码和关键结果；不要用旧日志或只写“应该通过”。
5. 命令无法运行时，说明缺失依赖/权限/硬件、已完成的替代检查和残余风险。

项目没有统一入口时，才按语言生态选择等价命令。例如 Python 可用仓库已有的 `pytest`/类型检查，Node.js 可用 `npm test`/`npm run build`，但不要在未检查配置前假设这些命令存在。

## 验证阶段反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 测试通过了就认为没问题 | 测试可能覆盖不足或阈值太宽 | 按领域契约覆盖能区分正确与错误的关键不变量 |
| 只看代码不看输出文件 | 代码逻辑正确但数据流有问题 | 验证输出文件中的实际值 |
| 跳过特定硬件测试 | 硬件相关的 bug 未被发现 | 无对应硬件环境用纯函数测试覆盖核心逻辑 |
| 验证完不汇总偏差报告 | 遗漏的步骤被遗忘 | 逐项对照计划生成偏差清单并分级 |
| 跳跃式排查 | 结果异常 → 直接怀疑方案不行 | 从最接近改动且最能区分假设的证据开始 |
| 跳过三 C | 改完"看起来跑通"就提交 | 三 C 是落地最低门槛 |
| 忽视边界 | 只测主路径 | 按风险覆盖受影响的关键边界和错误路径 |
