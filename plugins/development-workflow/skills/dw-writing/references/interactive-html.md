# 交互流程说明：先看主图，再读细节

供复杂流程、架构和方案对比的 HTML 按需使用。先确定读者要回答的问题，再选择总图、详图、卡片或术语说明；简单图文无需全部采用。本文依次说明图间衔接、就近解释和成品阅读检查，通用措辞与证据规则见 [dw-writing](../SKILL.md)。

## 总图和详图保持同一条线索

选一个可追踪的对象，在主图上标出起点、处理动作、分支条件和去向。箭头说明传递的是记录、结果、指令还是依赖关系；多种关系并存时给出图例。并行步骤说明汇合时等待什么，反馈箭头落到实际改变或重做的步骤。

需要解释某条箭头时，用同一对象展开其中的判断，详图的输入对应上图的输出，名称和条件保持一致。比如“提交申请 → 检查材料 → 审批”中的第二步，可以用一份明确标作演示的申请说明：检查哪些材料，缺项时交给谁补充，齐全后怎样进入审批。未记录的判断或中间值标为未知，不能用流畅动画补出因果。

比较多种方案时，让功能对应的步骤对齐，沿用相同输入、阅读方向和结果问题。形状、位置或数值的比较需要共同的比例、单位与参照；条件不同则分别注明。区分选择时的估计、采用决定和后续实测，历史方案、当前实现与待验证设想在相应位置标明状态。

## 在读者遇到问题的位置解释

所有卡片收起时，主图仍应能说明主要走向。卡面保留动作、关键结果和决定分支的条件。展开后就近回答：收到什么、怎样处理、为什么需要这一步、结果交给谁。问题用于选择细节，不要求每张简单卡片填四栏；难点用主图中的同一个例子走一遍。

术语解释说明正式名称、所指对象和本处用途，仅展开缩写仍不清楚时补短例子。章节入口、术语解释和证据链接各司其职。术语较多或跨页面复用时可维护共用词表，但要核对同名词在不同语境中的含义；自动加注释不能改坏原有证据链接。

使用有清楚名称、可见焦点且可由键盘操作的控件。卡片展开与术语解释应是可区分的动作，避免嵌套按钮、只有鼠标悬停才能看见的说明或只靠图像坐标才能点中的区域。可用有语义的文本或独立控件提供等价入口。

根据内容选择内联展开、就近浮层或对话框；采用相应的可访问交互语义。关闭后让焦点与阅读位置合理返回对应触发处，不强制所有说明使用模态窗口或相同关闭层级。存在叠层时逐层关闭，先回到下层说明，再回到主图；不要让背景控件意外响应同一次操作。

长说明应能用键盘、鼠标滚轮、滚动条拖动及适用的触摸操作读到末尾。窄屏下调整说明的位置或宽度，确保文本、关闭控件和最后一行可达。关键条件不能只藏在未展开的卡片中。

## 从实际交付入口检查

改动实际维护源，再按项目既有方式生成受影响页面。多入口或多格式交付时复用一致的内容，核对各入口中的名称、数字、状态、术语和证据。根据本次功能选择检查：

- 收起说明，沿一个具体输入走到结果，能说出分支依据、图间交接对象和反馈改变了哪一步。
- 展开关键卡片与其中一个术语，再关闭，确认解释正确且可以接着阅读下一步。键盘操作检查焦点可见、打开和关闭的顺序合理。
- 在宽屏、窄屏和长内容下实际滚动到末尾；有触摸支持时检查触摸操作，有缩放或视图切换时检查变化后的文字和点击区域仍对应。
- 约定离线或打印/PDF 交付时，按对应方式打开；关键释义和分支条件应以图例、脚注、附页或其他静态形式保留，离线资源及证据入口按交付约定可用。

记录实际检查了哪些入口和操作。生成成功只能说明产物已生成，未检查的交互或平台保持未验证。检查范围与证据结论按 [dw-verification](../../dw-verification/SKILL.md) 处理；不为普通文字润色增加全套浏览器或平台验收。
