# DeepSeek Harness bridge 4.0.0

The persistent-worker API and protocol 4 additions are specified in [agent communication](agent-communication.md). Existing task APIs remain available. The permanent compatibility guard now fences protocol 3 writers after an explicit quiescent migration; historical record layout remains schema 3.

## Goal and scope

Add an independently versioned Codex plugin to DW Marketplace. Codex submits a bounded task to one independently owned DeepSeek Harness runtime through the official SDK. The bridge provides submit, status, list, wait, result, continue, cancel, diagnostics and installed-capability inventory. Existing marketplace plugins keep their versions. Installation/configuration occurs within explicit user authorization.

## Execution contract

- The route is `deepseek-official / deepseek-flash`. Workload selects off/low/high; explicit off/low/high/max is supported. Checkpoints and truncation recovery use off. The bridge does not modify the caller's model policy or infer delegation authorization from installation.
- Pin SDK and its matching runtime to 0.2.1-rc.2. Use the SDK's supported Node runtime, not private Desktop IPC or GUI automation. Desktop login and GUI sessions are not reused.
- Multiple independent active tasks per bridge data directory, with one execution lease per task and no automatic task retry. A caller-supplied request ID makes submission idempotent; conflicting reuse is rejected.
- Each new task has its own Harness home and session. A continuation keeps its task's workspace, route, access mode and home. It creates a separate attempt; a task cannot be continued while running or cleanup is uncertain.
- MCP discovery and observations do not reserve execution or mutate tasks. A short registry transaction publishes admission, immutable record snapshots and task-scoped workspace claims. Each connection retains its identity across idle periods; another connection needs the task controlToken for continuation/cancellation. Cancellation mailboxes bind the exact attempt and lease nonce. Closing a connection cancels only its own runtimes. See [parallel conversations](parallel-conversations.md).
- Tasks survive as durable records. Observations never recover or interrupt another owner. Protocol 4 keeps a permanent compatibility guard at owner.lock to reject old hosts, plus task-scoped leases. Historical schema 1 records remain read-only. Uncertain cleanup retains only the affected task/workspace claim; lost registry ownership requires explicit reconciliation. No lock is stolen based on age or PID.
- Default access is read-only. New native profiles select supported DSH skills/files and, for workspace-write, optional sandboxed shell/teams; installed metadata alone remains insufficient use evidence. Built-in files exposes bounded read/list and optionally guarded writes; inference-only omits file tools. Local capability profiles can explicitly select pinned reviewed headless modules and skills. Installed desktop metadata is advisory, never automatic authority to load code. Exact runtime tool names are checked before prompting. Third-party modules and their dependencies are trusted code, responsible for their own path/effect policy; this is not an OS sandbox. See capabilities.md.
- Default file operations, including native files selection, stay inside the resolved task workspace. Both access modes use bridge list/read, with write available only in workspace-write; no raw third-party file component is mounted. Relative file paths resolve against task.workspace independently of the SDK process cwd. The process runs in private worker home; the existing HarnessClient initialization explicitly sets the session cwd to task.workspace. These tools reject absolute/parent paths, links and known protected metadata/credential names at every depth, and omit protected names from listings. This is a filename policy, not content-based secret detection; keep secrets out of ordinary delegated files. Skill catalogs and explicitly selected Shell/Team services have their own authority; this file boundary is not an OS sandbox for arbitrary third-party code. Bridge task records and the private worker home are outside the task workspace. Agent Teams resolves its relative `.agent-teams-bridge/<taskId>` state directory against the session cwd, placing it inside the workspace for new sessions. WorkspaceFiles protects that name at every depth and case for list/read/write and the guarded ops_replace adapter; native Team tools continue to manage it directly. Shell access is governed by its own authority and can still reach this workspace state. See the follow-up hardening in [capabilities.md](capabilities.md#obs-1--obs-2-后续加固).
- New omitted resource caps remain unspecified. Any explicit task-wide totals remain immutable across stages, eligible text-only recovery episodes and continuation. Native automatic sessions use SDK compaction first; budgeted mode supports durable stage chains without a fixed stage count. The agent/request hook prepares allowances before request freezing; llm/stream reserves and verifies them before dispatch. Initialization cannot spend. Generic failed-call retries and titles remain disabled. Native automatic compaction shares accounting; single-request and staged execution disable it. Missing usage is unknown; legacy records retain their historical rules. See [budget-reliability.md](budget-reliability.md). Third-party code bypassing the SDK is outside this gate. No exact currency cap is claimed. Cancellation closes the owned runtime and reports cleanup failure honestly.
- Subscribe before enqueue; wait through session/wait and a single-consumer delivery fence; inspect durable turn/end. No competing queue drainer may discard an in-flight event or reorder assistant text. Only a completed terminal is successful. Truncation, blocked, error, unknown termination and cleanup failure remain distinct from success. Runtime completion does not mean parent acceptance.
- Windows launch selects a configured existing Node executable and optionally decrypts a DPAPI credential into process memory. No secret is placed in argv/config/diagnostic output. Environment credentials have precedence. Desktop credentials remain separate.
- Return a concise task summary and paged result. Raw model/tool traffic is not echoed into MCP or written by the bridge. Harness keeps its own transcript in its isolated home. Bridge errors use safe categories, not raw provider stderr or credential-bearing exception text.

## Known path and saved-state boundaries

Native workspace-write exposes ops_replace as a bridge-owned, single-file literal replacement adapter, not the third-party recursive API. It requires path, pattern, replacement and the whole-file expectedSha256 from bridge_read. The adapter reads the whole bounded UTF-8 file (at most 256 KiB), preserves BOM and literal dollar sequences, then uses the existing write CAS/backup path; an operation cannot silently truncate later pages. Directory/glob/regex/recursive/dryRun operations are unsupported. Read-only does not register it. Temporary directories outside the task workspace are not allowed write roots. Existing custom capability modules remain explicitly trusted code with their own file/effect policy.

Before staging a replacement, the shared write path verifies the original-content backup: it must be an ordinary non-symbolic file with one hard link, and its SHA-256 must match the original file. A valid same-name backup is reusable. Missing, unreadable, linked or mismatched backups produce BACKUP_INVALID without changing the target or overwriting the problem backup; the owned workspace lock is released normally. Existing locks are never stolen. This protects the cooperative writer recovery contract; it does not make external editors or arbitrary third-party filesystem mutations transactional.

The built-in filename policy is case-insensitive. It includes the existing metadata/configuration names (`.git`, `.codex`, `.agents`, `.claude`, `.dsh`, `.aws`, `.ssh`, `.npmrc`, `.config`, `.agent-teams-bridge`, `node_modules`, `DeepSeekHarnessBridge`, `api-key.dpapi`, `.dsh-bridge-*`, `.env`/`.env.*`, and `credentials`/`.credentials` with optional dot suffixes), plus `.envrc`/`.envrc.*`, `.netrc`, `_netrc`, `.pgpass`, `pgpass.conf`, `.git-credentials`, `.pypirc`, `.kube`, `.docker`, and private-key names `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519` (including `_sk` suffixes). Public `.pub` files and ordinary files such as `package.json`, `README.md`, and `config.json` remain available. Renamed credentials and secrets embedded in ordinary files are outside this policy, as are trusted custom modules' own file access.

Saved task loading requires at least one attempt (exactly one for single-request; the legacy maximum remains 16) with consecutive numbers, unique valid request IDs, SHA-256 fingerprints, parseable start timestamps, and recognized status/cleanup fields before registering the task. Invalid records fail with `INVALID_STATE` through the existing fail-closed load path; the source `task.json` and ownership lock remain for operator reconciliation. A later connection sees `STATE_LOCKED`; it must not delete the lock or silently skip the record. Historical optional result/planning fields remain optional.

## Implementation order and acceptance

1. Add behavioral tests and verify the missing behavior fails.
2. Implement durable task state, single ownership, idempotency, timeout/cancel, continuation and bounded results using a fake runner.
3. Implement official SDK adapter and constrained filesystem tools. Verify SDK transport with a local fake JSON-RPC runtime and exercise filesystem boundaries.
4. Wire MCP tools and plugin/marketplace metadata. Exercise the real MCP stdio boundary without a paid model call; validate package contents and existing marketplace checks.
5. Review standards and specification independently; repair concrete findings and repeat affected tests.

Real DeepSeek inference, live Codex plugin installation, desktop session visibility, performance claims and publication require their own evidence. Zero-model protocol tests must not be reported as live Flash validation.
